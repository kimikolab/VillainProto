## 0. 出発点

第15期で**交互作用が実在することが確定した**。寄与する7波の21ペア全部が ρ < 0.90、既存5波の中だけでも 第2波 × 第4波 が ρ 0.16。名指しでは 第4波→R10 で 毒 が 75.0%→100.0%、速攻 が 100.0%→21.0%。

**ところが予測できない。** 「効き方の一致度」と「順位相関」の関係が r = 0.16。第13期の台間の入れ替わり（最良 r² 0.19）と**同じ形の壁**で、目的変数を突破度から勝率に替えても再現した。

### 「予測できない」は悪いことではないかもしれない

単発戦が主なら、むしろ望ましい可能性がある。

- 予測できる（総攻が高いほど強い）→ プレイヤーは計算で最適解を出せる。**編成パズルにならない**
- 予測できない（試さないと分からない）→ **試行錯誤に意味が生まれる**

コンセプトの中心ループは「ビルド → 送り出す → 観察 → 学び → 組み直す」で、**観察と学びが要るのは予測できないから**。

**ただし「予測できない」と「学べない」は違う。**

- プレイヤーが**試して学べる**（毒は第4波に弱く R10 に強い、と気づける）なら編成パズル
- 試しても**法則が見えない**なら、ただのガチャ

`power` の15特徴量で予測できないことは、**プレイヤーが学べないことを意味しない**。特徴量が「総攻」「総HP」のような集計量ばかりで、**プレイヤーが実際に見ている情報**（誰がどの駒を殴るか、貫きが後列に届くか、範囲が何体巻き込むか、毒が乗り切る前に敵が落ちるか）を含んでいない。

**この作業は「法則が無い」のか「特徴量が悪い」のかを決める。**

## 2. Phase GA — 個別事例の解剖

### 2-1. 対象

**第15期で入れ替わりが最も大きかったペアから、3組を選ぶ。** 最低限これを含める:

| ペア | 名指しの事例 |
|---|---|
| 第4波 × R10 板金6 | 毒 75.0%→100.0% / 速攻 100.0%→21.0% |
| 第2波 × 第4波 | ρ 0.16。**既存5波の中の入れ替わり**なので最も重要 |
| 第4波 × R8 重甲5 | ρ 0.24 |

各ペアで、**順位が最も動いた編成を上下2つずつ**選ぶ。合計 12 事例程度。

### 2-2. やること

**戦闘ログ（`demo` / `ptrace` と同じ要領）を読んで、なぜそうなるかを言葉で説明する。** 統計ではない。

説明に使ってよい材料:

- 決着ターン数、各ターンの盤面（誰が生きているか）
- 誰が誰を殴ったか、貫きが後列に届いたか、範囲が何体を巻き込んだか
- 毒・燃焼のスタックが何ターン目に何段になったか、敵が落ちる前に乗り切ったか
- 敵の def（HP / 攻撃 / 速度 / パターン / 体数）

**参考になる既存の数値**（`UnitCatalog` から。**新しく作らない**）:

| def | HP | 攻 | 速 |
|---|--:|--:|--:|
| `Warden` 城塞の重装兵（第4波 前列×3） | 145 | 12 | 3 |
| `ZealotPlate` 板金鎧の狂信者（R10 ×6） | 60 | 16 | 5 |
| `ZealotGreat` 重甲の狂信者（R8 ×5） | 90 | 16 | 5 |

第4波は **145HP × 3 + 司祭 + 詠唱兵**、R10 は **60HP × 6**。**総HPは近いが、個体HPと体数が正反対**。第6〜7期で見つけた「符号は個体HP、大きさは体数」の原理が、代金ではなく**勝敗**でも効いている可能性がある。

### 2-3. 出すもの

事例ごとに:

1. **何が起きたか**（1〜3文）
2. **その説明を数値に変換する案**。例:「毒が乗り切る前に敵が落ちる」→ `敵の個体HP ÷ 味方の1ターンあたり打点`
3. **その数値が Phase GB の特徴量として使えるか**

**説明が付かない事例があれば、それも報告する。** 全12事例に説明が付くなら「法則はある」、半分以上に付かないなら「本当に読めない」に傾く。

### 2-4. 受け入れ条件

- 18モード差分ゼロ
- 12事例の説明（推測は推測と明記）
- 特徴量への変換案（Phase GB で使う）

## 3. Phase GB — 敵側の特徴量

### 3-1. なぜ

**いまの `power` は編成側の特徴量しか持っていない。** 交互作用は 編成 × 波 なのに、**波の側を数値化していない。** 第12期以来ずっと片側だけで予測しようとしていたので、**予測できなくて当然だった可能性がある。**

### 3-2. 足す特徴量（敵側）

編成側と対称になるように取る。**既存の `UnitDef` と `Formation` から計算できるものだけ**（戦わずに分かる）。

| 特徴量 | 定義 |
|---|---|
| 敵体数 | 波の駒数 |
| 敵総HP | 定義上の最大HPの合計 |
| 敵総攻 | `Attack` の合計 |
| 敵の個体HP中央値 | **第6〜7期の原理の主役** |
| 敵の最大個体HP | 一番硬い駒 |
| 敵の1体あたり攻撃 | 敵総攻 ÷ 敵体数 |
| 敵の範囲枚数 | 薙ぎ／全体の駒数 |
| 敵の貫き枚数 | 貫きの駒数 |
| 敵の平均速度 | |

### 3-3. 交互作用項

**編成特徴量 × 敵特徴量の積**で予測する。理屈からいって、交互作用を予測するには両側が要る。

ただし **n が問題**。31編成 × 7波 = 217 点あるが、**編成も波も繰り返しなので独立ではない**。過学習を避けるため:

- **積の候補は、Phase GA の解剖から出てきたものに限る。** 総当たりで作らない（編成13 × 敵9 = 117 通りの積を全部試すと、n=217 では必ず何かが当たる）
- 加えて、**理屈で先に決めた積を数個**だけ。例:
  - `味方の範囲枚数 × 敵体数`（範囲は体数が多いほど効く。第6〜7期の原理）
  - `味方の1発打点 ÷ 敵の個体HP中央値`（一撃圏。**第13期で棄却した閾値仮説の、敵側を入れた版**）
  - `味方の総攻 ÷ 敵の総HP`（決着の速さ）
  - `敵の貫き枚数 × 味方の後列HP`（貫きが後列に届く編成ほど損）
- **候補は全部で10個以内**。選んだ理由を全部書く

### 3-4. 測ること

目的変数は**波ごとの単発勝率**（第15期と同じ、寄与する7波）。

1. 各交互作用項と勝率の相関（**波をまたいで、217点をプールした状態で**）
2. **第15期の編成側だけの説明力（波ごと r² 0.059〜0.341）と比較する**
3. **最も効く積を1つ選び、その残差を見る**。残差の大きい事例が Phase GA で解剖したものと一致するか

### 3-5. 判定

| 観測 | 結論 |
|---|---|
| 積を入れると説明力が明確に上がる | **交互作用は読める。** 特徴量が悪かっただけ。**プレイヤーも学べる**ということなので、ステージ設計に使える |
| 積を入れても上がらないが、Phase GA の解剖では説明が付いた | **人間には読めるが数値化できていない。** 説明の言葉を、より良い特徴量に翻訳し直す余地がある |
| 積も効かず、解剖でも説明が付かない | **本当に読めない。** ガチャに近い。**その場合は「読める交互作用」を設計で作りにいく必要がある** |

### 3-6. 受け入れ条件

- 18モード差分ゼロ
- 積の候補が10個以内で、選んだ理由が全部書かれている
- **総当たりで積を作っていないこと**

## 4. Phase GC — 記録と報告

### 4.1 README に書くこと

- **「予測できない」の解釈**。単発が主なら試行錯誤の余地として望ましい可能性があること、ただし「学べる」ことが条件であること
- Phase GA の解剖結果。**どの事例に説明が付いたか**
- 敵側の特徴量を足した結果。§3-5 のどの行か
- **第12期以来、編成側の特徴量だけで予測しようとしていた**という反省。交互作用には両側が要る

### 4.2 報告してほしいこと

1. **12事例のうち、説明が付いたのはいくつか。** 付かなかったものは何が分からなかったか
2. **説明に共通する構造はあるか。** 個体HP と体数の話に収束するか、それとも事例ごとにバラバラか
3. **積を入れて説明力は上がったか。** 第15期の r² と並べて
4. **最も効いた積は何か。** それは Phase GA の解剖から出たものか、理屈で決めたものか
5. **§3-5 のどの行か。** 3行目なら、次は「読める交互作用を設計で作る」話になる

## 5. 作業ルール

1. 計画書のコミット（第15期分も）→ GA → GB → GC の順。**フェーズを跨いで1コミットにしない**
2. コミットメッセージに「動いた docs/ の行」を書く。**全フェーズ差分ゼロのはず**

4. CONTRIBUTING.md のチェックリストを通す
5. 長時間ジョブは前景で待ち切る。`layout` は走らせない
6. **何も直さない。** `BattleCore` に触れる必要が出たら方法が間違っているサイン
7. 以下を見つけたら**実装前に止まって報告する**:
   - Phase GA で、解剖しようとした事例が seed によって結果が大きく振れる場合（**平均で 75%→100% でも、個別の試行では別のことが起きているかもしれない**）
   - 積の候補を10個に絞れない場合。**総当たりに逃げず、絞れない理由を報告する**
   - `docs/` が動いた場合
