## 1. Phase 0 —— 調査（実装の前に取った）

### Q0-1 —— `ModifyAttack` が対象を受け取らないこと

`BattleCore/Traits.cs:294`:

```csharp
public virtual int ModifyAttack(UnitState self, int atk) => atk;
```

**`UnitState self` と `int atk` の2つだけ。** `BattleContext` も対象も受け取らない。
上書きは **5 件**（`SniperTrait` / `OverbearTrait` / `ThinBladeTrait` / `PerverseTrait` / `PyreTrait`）。

**`FinisherTrait` の doc の主張は今も正しい**——`BattleEngine.cs:3676` のコメントと実装が一致する:

```csharp
// 止め（第53期）。**倍率は攻撃の解決時に掛ける**——`Trait.ModifyAttack` は対象を
// 受け取らないので「相手が標を持つか」で分岐できない
if (FinisherActive && pattern == AttackPattern.Single && actor.HasTrait(TraitId.Finisher))
    if (target.RawCounter(StatusKeys.Marked) > 0) atk *= Finisher.Multiplier;
```

薄刃（第75期・`BattleEngine.cs:3641`）も**まったく同じ理由で同じ場所**にある。
**「対象を見る条件」は engine 側にしか置けない。**

> **したがって §0-2 の前提は成立する**——「標的が燃えていれば重い」は書けない。
> **書けるのは「盤面の燃えている敵の数を読む」形だけ**である。

### Q0-2 —— `UnitState.Board` から敵を引けるか

**引ける。新しい窓口は要らない。**

`UnitState.Board`（`Models.cs:146`）は `BattleContext.Add` が差す盤面参照で、
doc に**足した理由がそのまま書いてある**:

> 足した理由は1つだけ——`Trait.ModifyAttack` が `self` しか受け取らないので、
> **「隣に誰がいるか」を攻撃力の条件にする特性が書けない**（驕り・第46期）。

前例は `OverbearTrait.Ready`（`Traits.cs:3136`）:

```csharp
BattleContext? board = self.Board;
if (board is null) return false;          // 盤面の外で作られた駒
foreach (UnitState a in board.AllUnits)
{
    if (a == self || !a.IsAlive || a.TeamId != self.TeamId) continue;   // ← 味方だけ
    ...
}
```

**この行の `!=` を `==` にすれば敵になる。** `AllUnits` は `BattleContext` の公開プロパティで、
`LivingMembers` ではなく `AllUnits` を走るのも前例どおり（`ModifyAttack` は攻撃のたびに呼ばれるので、
`ToList` するスナップショットを毎回確保しない）。

**`Board` が null のときは不活性**にする（第46期の明文の規則）。

### Q0-3 —— `ModifyAttack` が呼ばれる回数

**1回の振りにつき 1 回。** `PerformAttack`（`BattleEngine.cs:3634`）は

```csharp
int atk = attackPercent == 100 ? actor.CurrentAttack : actor.CurrentAttack * attackPercent / 100;
```

で**打点を1度だけ作り**、薙ぎの巻き込みは同じ `dealt` から `* SecondaryPercent / 100` を引く。
**貫きの段（`ResolvePierce`）も同じ `atk` を受け取る。**

> **したがって「振るたびに盤面を1度読む」形になる。**（望ましい）

**ただし計数を `ModifyAttack` の中に置いてはいけない**——`CurrentAttack` は
駆り立ての選択・転嫁の流し先・`StatSnapshot`・棘/仇討ち/責め苦の反撃量からも読まれるので、
数えると「振った回数」ではなく「**読まれた回数**」になる（`OverbearTrait` の明文の警告）。

### Q0-4 —— ボルグが1戦で作れる燃焼の上限

`CinderTrait.OnAfterAttack`（`Traits.cs:6597`）は

```csharp
ctx.Ignite(target, source: self);                       // 敵 ＝ 主目標だけ
foreach (... ally ...) ctx.Ignite(ally, friendly: true, source: self);   // 隣接する味方
```

`OnAfterAttack` は**攻撃1回につき1度・主目標に対してのみ**（engine の規則）なので、
**薙ぎで3体に当たっても着火は1体**。`Ignite`（`BattleEngine.cs:626`）は

```csharp
int turns = BurnRules.Turns;      // = 3
```

を**設定**する（加算しない＝非スタック）。`TickStatuses` がターン頭に1ずつ減らすので、
T に点けた火は T+1・T+2・T+3 に効いて T+4 の頭で消える。

> **ボルグ単独で同時に燃やせる敵は最大 3 体**（毎ターン別の敵を主目標にし、1体も落ちなかった場合）。
> 実際には敵が落ちる・同じ敵を殴り直す（再着火で 3 に戻るだけ）ので、**これは届かない上限**である。

### Q0-10 —— 過去に「敵の状態を読んで威力を変える」機構を測っていないか

`design/` を grep すると `Finisher` は **11 ファイル**・`FinisherRule` は **7 ファイル**に出る。

拾った測定:

- **窓口の位置**: 「倍率 ＝ `PerformAttack` が `atk` を作った直後。`Trait.ModifyAttack` は
  **対象を受け取らない**ので分岐できない」（§4 の表）。**Q0-1 と同じ結論に独立に到達している。**
- **倍率の効き**: `Multiplier` 1 → 2 でトメの与ダメ 63.0 → 110.4（**+47.4 / 戦**）。

## 2. 実装（段1）

`TraitId.Wildfire`（火勢）／`WildfireTrait`／`WildfireMode`／`WildfireRule(Mode, Amount)` を足した。
**既定は `WildfireRule.Off`** で、**保持者は `UnitCatalog.All` に 0 枚**（診断のローカルの `UnitDef` だけが持つ）。

```csharp
public override int ModifyAttack(UnitState self, int atk)
{
    BattleContext? board = self.Board;
    if (board is null) return atk;              // 盤面の外。不活性（第46期）
    WildfireRule rule = board.Wildfire;
    if (!rule.Active) return atk;               // 既定は Off。比較1つで抜ける
    int n = BurningFoes(board, self);
    if (n <= 0) return atk;
    return rule.Mode switch
    {
        WildfireMode.Add   => atk + rule.Amount * n,               // V1
        WildfireMode.Scale => atk * (100 + rule.Amount * n) / 100, // V2
        _                  => atk * (100 + rule.Amount) / 100,     // V3（二値）
    };
}
```

**engine に足したのは計数1行と、その中身だけ**（`NoteWildfireSwing`）。
**規則で分岐している箇所は 0 件**（自己検査の A4）。
計数を `ModifyAttack` の中に置かなかったのは Q0-3 の理由——
`CurrentAttack` は駆り立ての選択・転嫁の流し先・`StatSnapshot`・反撃量からも読まれるので、
あそこで数えると**「振った回数」ではなく「読まれた回数」**になる（驕りの明文）。

## 4. 段2 に進む条件の判定（指示書 §5-1）—— **落ちた**

| 版 | 1 発火率 ≥ 40% | **2 燃敵 ≥ 1.0** | 3 与ダメと撃破が両方増える | 4 分散 ≠ 0 | 判定 |

| V1 | ○ | **×**（0.80 / 0.44） | ○ | ○ | **落ちる** |
| V2 | ○ | **×**（0.79 / 0.44） | ○ | ○ | **落ちる** |
| V3 | ○ | **×**（0.75 / 0.43） | ○ | ○ | **落ちる** |

> **3 版とも条件 2 で落ちた。したがって段2 には進んでいない。**
> **`WildfireRule` の既定は `Off` のまま残置**で、**盤面は1ビットも動いていない**
> （第130期の `EmberRule` と同じ扱い）。

**線を結果の後で緩めていない**（第64期）。
条件 2 は指示書が **P1（同時に燃えている敵は平均 1.5〜2.5 体）から引いた線**で、
**実測は 0.75〜0.87（台1）／ 0.43〜0.46（台2）＝ 予測の半分以下**だった。

**この落ち方は規約 (G11) そのものである**——
「**判定の線を引く前に、対照側の実測値を見る。**」
**V0（対照）の燃敵は 0.87 / 0.46 で、`run` を1回回せば実装前に出せた量**だった。
**線の高さを決めたのは予測であって、盤面ではなかった。**

**残しておく事実**: 条件 2 以外は3版とも全部通っている。
**機構は完全に動いた**——`台2` の勝率は **+18.5 / +19.9 / +26.8pt**、
与ダメは +15.1〜+41.6、撃破は +0.32〜+0.77、分散は 5.04〜11.80 で 0 ではない。
**落ちたのは「効かなかったから」ではなく「読む対象が予測の半分しか立たなかったから」**である。

### 5-1. P1 が外れた理由 —— 「作れる上限」と「実際に立つ数」は別

Q0-4 で**ボルグ単独の上限は 3 体**と導いたが、**実測の最大は 2 で、平均は 1 を切る**。
理由は上限の導出が置いた前提「**毎ターン別の敵を主目標にする**」が、盤面で成り立たないことにある:

- 標的選択は**前列が生きている限り前列しか含まない**（`TargetPool` の中核規則）ので、
  ボルグは**同じ前列の敵を殴り続ける**。再着火は残ターンを 3 に**戻すだけ**（非スタック）で、
  **燃えている体数は増えない。**
- その敵が落ちると**燃えている体が1つ消える**。つまり
  **「火を増やす動作」と「火を消す動作」が同じ一振りの中にある。**

> **系: 「その機構が同時にいくつ在庫を持てるか」を、供給の回数と持続の積で数えると必ず上振れする。**
> **在庫が増えるのは供給が<u>新しい相手</u>に向いたときだけ**で、
> それを決めているのは供給側の周期ではなく**標的選択**である。
> 第59期「『一度きりの供給』は蘇生役がいると一度きりでなくなる」の逆側——
> **こちらは「毎ターンの供給」が、標的選択のせいで実質「一度きり」に潰れている。**

### 5-2. P2 が外れた理由 —— 発火率は台が決める

台1 68.9% / 台2 42.1% と、**同じ駒・同じ規則で 27pt 違う**。
差は**もう1枚の火力（ドルガ攻38）が、燃えている敵を先に倒すこと**である。
**これは欠陥ではなく P6 そのもの**——盤面を読む機構なので、
**味方が強いほど自分の条件が消える。**

> **発火率は保持者の性質ではなく、同席する火力の性質である。**

## 6. 第132期の則は予測どおり働いたか（指示書 §7 の 6）

> **上限は「1発の上側」を平準化する装置なので、上限の下では体数の多い型が有利になる。
> 切られる総量と結果は逆を向く。**（第132期）

**薙ぎに一撃の倍率を足すと、確かに上限に当たるようになった**——
V0 は第四波で **1 度も切られない**（0.00 回/戦）のに、V1 / V2 は **1.40 / 1.39 回/戦**切られる。
**上限に触れる回数を作ったのは倍率のほうである。**

**ただし切られた「量」は 0.6〜2.8 点/戦にしかならない。** 内訳は表Cで割れている:

    V1（加算・+4/体）    第四波 1.40 回 / **1.4 点** ＝ 1 回あたり **1.0 点**
    V2（乗算・×1.25/体） 第四波 1.39 回 / **2.8 点** ＝ 1 回あたり **2.0 点**
    V3（二値・×1.40）    第四波 **0.00 回 / 0.0 点**

> **同じ回数だけ上限に触れているのに、乗算は加算のちょうど 2 倍を捨てている。**
> **第132期の則が、機構の形の差としてそのまま出た**
> ——「乗算は1発を大きくするので上限に食われる／加算は上限の下でも素直に効く」
> （指示書 §3-2 の選び方の 2）。

**V3 が 0.00 回なのは意外だった。** 二値は上乗せ平均が最も大きい（4.32 / 2.83）のに
**一度も上限に届いていない**——V3 は**燃えている敵が1体でもいれば一律 ×1.40** なので、
**素の打点が低いターンにも均等に乗る**。加算と比例は**燃えている敵が2体のときに跳ねる**ので、
**上限に触れるのは「たまたま2体燃えていた振り」だけ**である。

> **上限に課金されるのは「平均の大きさ」ではなく「分布の上側の厚み」**である。
> 第132期は型（単体・薙ぎ・貫き・全体）でこれを見たが、**同じことが1つの型の中でも起きる。**

**なお P3 の「第四波では伸びない」は、この期の器具では判定できない**
——段2 に進んでいないので**波別の勝率の伸びを測っていない**。
測れたのは**上限に触れた回数と量**（A7）までである。
**第118期「他の期の数値を判定の線にするときは、その線がこの器具で到達可能かを先に見る」**と同じ形で、
**P3 は段2 の器具でしか判定できない予測を段1 の指示書に書いていた。**

## 8. 気づいたが手を付けなかったこと（指示書 §8 に足す）

1. **条件 2 の線は、実装前に `V0` を1回回せば正しく引けた。** 規約 (G11) を
