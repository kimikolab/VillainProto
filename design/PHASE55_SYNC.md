    dotnet run --project BattleSim -c Release 0 audit

**戦闘を1回も回さない。`docs/` に何も書かない**（生成物を1つ足すと腐るものが1つ増える）。
実測 1 秒。

**判定は「現行の編成名がその生成物に1つ残らず現れるか」の1本だけ。**
指示書は「行数を読んで編成数と整合しているか」と書いているが、
**行数を直に比べる形にはしなかった**——理由は2つ:

1. **ファイルごとに 1編成あたりの行数が違う**（`balance` 1行 / `chain` 1行 / `ablation` 10行 /
   `pulse` 11行 / `layout` 19行 / `reseat` 25行 / `engage` は3節に分かれる）。
   係数表を持つと、**表の書式を1列足すたびに検出器が嘘になる**
2. **名前の有無は書式に依存しない。** 編成を足しても消しても改名しても検出できる

行数は表に出すが**判定には使わない**（腐りの深さを人が読むための情報）。

**陰性でないことを確かめてある**（陽性対照）。旧 `docs/chain.md` を書き戻して回すと:

    - 責め苦 (トウ×シガ) ...

**「0 件でした」は「効いている」と「検出器が壊れている」の区別が付かない**
（第37期 `sever sale` の作法）ので、旧ファイルを陽性対照に使った。

## 4. 義務の切り分けと、その理由

`CONTRIBUTING.md` を実態に合わせて書き直した。**規約を実態に合わせたのであって、逆ではない。**

| 範囲 | 対象 | 合計 | いつ |
|---|---|--:|---|
| **毎回** | `compare` / `dump` / **`audit`** | 11s | 全ての変更で |
| **編成が増減したとき** | 編成数依存の6ファイル全部 | 約10分 | `CompareBuilds()` を触ったとき |
| **仕様変更のとき** | 加えて `layout` / `reseat` | — | 攻撃パターン・盤面・特性の挙動が動いたとき |

**理由。**

- **`layout` を「毎回」から外した。** 指示書の推奨（重いものは任意）に従ったが、
  根拠は所要ではなく**腐り方**である。Q2 のとおり6ファイルは**同じ世代で一斉に古くなった**
  ——腐る条件は「重いかどうか」ではなく「`CompareBuilds()` を触ったか」の1つだけ。
  数値を1つ動かしただけの変更では `layout.md` は古くならないので、毎回回すのは純粋な無駄
- **代わりに `audit` を「毎回」に入れた。** 11秒に1秒足すだけで、
  **飛ばしたことが必ず検出される**。手順4 の `layout` が守られなかったのは
  「40分かかる」と書いてあったからで、**義務を重くすると守られなくなり、
  守られなかったことが誰にも見えない**——これが今回の穴の作られ方そのものだった
- **`layout` / `reseat` は仕様変更にも紐付けた。** 「配置が旧ルール前提のまま残ると、
  変更が過剰だったように見える」（後衛特化+後備え 旧配置3.5% / 再探索後26.0%）は
  今も有効な事故なので、**編成の増減とは別の条件として残した**
- **`reseat` の2分割手順を明記した。** 367秒は1回のツール呼び出しに収まるが、
  合計603秒（全部）は収まらない。**分け方を規約に書いておかないと、
  次に誰かが背景に回して刈られる**
