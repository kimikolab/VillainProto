# 第137期 指示書 —— 砕けの鍵を自前にする（ヒビ）

**HEAD 前提: 第136期 `9ccae6d`**（ガルドの受け流し N=2 を採った期）。

**この期の一文**:
> 砕け（ヒビ）の供給トリガーを「範囲攻撃を受けると」から「毎ターン自分を砕く」へ差し替え、
> **鍵が敵依存から自前になると働くか**を測る。

本書は自己完結している。リポジトリ外の文書は参照しない。

## 0. なぜこれをやるか（背景・この期の文脈）

第136期でガルドが「**単体で死ぬタンク**」の答えになった。`docs/harm.md` の表Aで
ガルドの範囲被弾が小さく（単体で死ぬ組）、対して範囲で死ぬ組（ササ・ウケ・ワタ）が別にいる。
受け流しは単体の一撃しか消さないので、**範囲側の答えはガルドからは移せない**。

範囲側の手は2つしかない。

| 手 | 触る場所 | この期で採るか |
|---|---|---|
| 庇い・標的の介入を範囲にも効かせる | `CLAUDE.md` が設計の中核と明記している一文 | **採らない**（独立した期が要る） |
| **破片（`StatusKeys.Armor`）を厚くする** | 駒の定義と1つの規則 | **これを採る** |

破片を選ぶ理由:

1. **破片は `AcceptsSupport` を貫通する唯一の資源**。`ShatterTrait` / `ScaleTrait` の doc が
   どちらも明記している通り、`Stoic`（ガルド）に届く支援はこれしかない。
   **その「誰の助けも届かない駒」が第136期に主力になった**ので、この性質が初めて現実の文脈を持つ
2. **鍵が一番遠い**。現行の供給条件は「**範囲攻撃を受けると**」＝敵が何を振るかに完全依存で、
   第129期の密度表（自前 ×0.95 → 自分の被弾 ×0.74 → 撃破 ×0.72 → 味方の被弾 ×0.65 → 標 ×0.55）の
   どれよりも遠い。**敵依存の鍵は一度も測っていない**
3. **engine に足す規則がゼロ**。破片のプール・消費・上限との順序（上限の手前で引かれる）は既にある

## 1. 予測（**実装前に書き切って報告書に残す。外れたら消さずに残す**）

Q0-1 の実測値を入れてから確定させること。方向だけ先に書く。

1. **`鱗改 (ウロ×ヒビ)` が最も大きく動く。** ウロは破片を読んで貫きになる（`ModifyPattern`）＝
   **変換率が最も高い受け手**なので、供給が安定すると貫きの立っているターン数（`ScaleWornTurns`）が伸びる。
   **符号はプラスを予測する。** ただしウロは振るたび剥がれる二重支出なので、伸び方は線形にならない
2. **`範囲耐性 (ヒビ×ボルグ)` は小さくしか動かない、あるいは下がる。**
   ボルグの薙ぎの巻き込みでヒビは**開幕から砕けている**（`鱗改` の preset コメントが明記）ので、
   この行では現行の鍵が既に近い。**新方式は自傷ぶんヒビが早く死ぬので下振れしうる**
3. **`仇討ち×砕け (ヒビ×ザン)` は上がる。** 敵の範囲を待たずに供給が出る
4. **ヒビの死亡率は上がり、生存Tは下がる。** 自傷ぶん。これは代金なので下がること自体は不採用の理由にしない
5. **ガルドを含む行で、ガルドの被弾無効化率（受け流し）と破片の soak が食い合う可能性がある。**
   受け流しは単体の一撃を丸ごと消し、破片はその手前で引かれるプールなので、
   **破片が先に吸うと受け流しの在庫が減らない＝ガルドが長持ちする**方向を予測する。
   逆に「破片が無駄撃ちになる」方向もありうるので、**どちらに出たかを必ず切り分ける**
6. **既定（`Passive`）では `compare` 61行 × 5波の 305 セルが 0件差分**（§3-1）

> **予測は軸名ではなく編成表の駒を数えて書く**（既定の作法）。
> **予測が読む量が実装のどこから来るかを1回たどる**（第130期に「主判定にホタの燃焼率を置いたが
> ホタは自分に配らないので定数だった」を踏んだ。同じ形で3回目だった）。
> 今回なら「`ScaleWornTurns` は誰が増やすか」を実際にコードで追ってから予測に使うこと。

## 2. 実装

### 2-1. `ShatterRule` を足す（`ScaleRule` / `BearRule` / `YokeRule` と同じ作法）

```csharp
/// <summary>砕けの供給の出どころ。診断が版を差し替えるためだけの窓口。</summary>
public readonly record struct ShatterRule(ShatterMode Mode, int SelfCostPerTurn)
{
    public static ShatterRule Default => new(ShatterMode.Passive, 0);
}

public enum ShatterMode
{
    /// <summary>現行。範囲攻撃を浴びた量の 25% を配る（敵依存の鍵）。</summary>
    Passive,
    /// <summary>新。毎ターン自分を砕いて、払った量と同じだけ配る（自前の鍵）。</summary>
    Turn,
    /// <summary>対照。両方走らせる。**採用候補ではない**（どちらが効いたか分離できない）。</summary>
    Both
}
```

- `BattleContext` に `public ShatterRule Shatter { get; }` を生やす。
  **static のノブにしない**（`YokeRule` / `BearRule` / `ScaleRule` と同じ理由）
- **既定は `Passive`。** 味方側の駒なので、ヒビを入れない限り既存の行は1バイトも動かない
  ——それ自体が回帰チェックになる（`BearRule` の doc と同じ論法）

### 2-2. `ShatterTrait` の改修

`OnDamaged` の中身は**1行も書き換えない**。先頭に `if (ctx.Shatter.Mode == ShatterMode.Turn) return;` を足すだけ。

`OnTurnStart` を足す:

```
Mode が Turn または Both のとき:
  cost = ctx.Shatter.SelfCostPerTurn
  cost <= 0 なら何もしない
  自分に cost のダメージを入れる（§2-3 の引数で）
  実際に減った HP と同じ量を破片として味方全員へ配る
    （自分には配らない／AcceptsSupport は見ない ← 現行の Distribute と完全に共有する）
```

**配り先のロジックは現行と1バイトも変えない。** 現行の `OnDamaged` の中の配布部分を
`private static int Distribute(BattleContext ctx, UnitState self, int shards)` に**抽出**して両方から呼ぶ。

> **`MostHurtAlly` は使わない。** あれは `AcceptsSupport` を通すので**ガルドが除外される**——
> 破片の設計意図（回復が届かない駒に唯一届く）と正面から矛盾する。
> 「最も被弾している味方に配る」案はこの期では採らない。配り先はこの期の変数ではない（§6）。

**「実際に減った HP と同じ量」にするのが要点。** 払った量と配る量が同じなら、
一文が「自分を砕いて破片を撒く」の1文で済み、変換率という2つ目のノブが要らない。
脆弱で代金が1.5倍になるなら**配る量も1.5倍になる**（浴びるほど配れる、という現行の設計言語のまま）。

### 2-3. 自傷は `ApplyDamage` を通す

```csharp
ctx.ApplyDamage(self, cost, source: self, isFriendlyFire: true, lethal: false, spillWound: false);
```

- **通す理由**: ワタの `HpCostPerDull` の前例（doc に明記）。
  庇う・分かち・巨躯・後備え・棘守りが割り込むので、**「代金を誰かに肩代わりさせる」が編成の選択肢になる**。
  そのぶん意図した代金が効かなくなるので、**自弁率を必ず数える**（`relay` の前例。§4-1）
- `lethal: false`（Q0-5 の結果次第で調整）
- `spillWound: false`（自傷で傷を撒くつもりはない。Q0-4 で既定を確認して合わせる）
- **脆弱（`FrailTrait`）は外さない。** 自傷も1.5倍になるが、配る量も同じだけ増えるので
  「脆いほど多く配れる」という現行のマイナスの意味がそのまま自前の鍵に移る。
  **ただし Q0-4 で「脆弱が自傷に乗らない」と分かったらそのままにして報告する**（後から足さない）

### 2-4. 駒のテキスト（`UnitDef.Hibi`）は**この期では変えない**

採用が決まってから一文を直す。採用時の案:

- `PlusText`: 「毎ターン自分を砕き、砕けた分を破片として味方全員に配る（HPの前に削られる／回復を受け付けない味方にも届く）」
- `MinusText`: 「受けるダメージが5割増し / 配るほど自分が減る」

**`Advances = false`・HP55・攻5・速3 は動かさない。** この期の変数は鍵の出どころ1つだけ。

## 4. 測定

### 4-1. 診断に足すもの（無ければ足す。Q0-2 の結果次第）

`BattleContext` に計数を足す。**盤面には一切触らない**（`Dull` の計数と同じ扱い）。

| 計数 | 内容 |
|---|---|
| `ShatterTicks` | 砕けが発火した回数 |
| `ShatterGiven` | 配った破片の総量 |
| `ShatterSoaked` | そのうち実際にダメージを吸った量 |
| `ShatterPaid` / `ShatterPaidSelf` | 代金の総額 と そのうちヒビが自弁した額（自弁率の分子・分母） |

`ShatterSoaked` は `ApplyDamage` の中で `Armor` が削られる箇所（`target.SetCounter(StatusKeys.Armor, armor - soak)` 付近）で数える。
**出どころ別に割る必要は無い**——集約（ウケ）と砕けが同じ行に同居するのは `compare` では稀なので、
まず陣営合計で足りる。同居する行があるなら Q0-3 で見つかるはずなので、そのときだけ分ける。

**`docs/balance.md` には列を足さない**（自己検査が壊れる。第126期に61行293件のずれ）。
足すなら別ファイル（`quality.md` / `stock.md` / `harm.md` の前例）。

### 4-2. 掃引

`SelfCostPerTurn` を **Q0-1 の実測から引いた3点**で振る。
紙から決めず、「現行の配布総量/戦 ÷ ヒビの平均生存T」を中心に上下1点ずつ。

各点で:

- **主判定**: Q0-3 で決めた集合（`compare` の3行 ＋ ローカル台）× 第2〜5波 × seed 0..199。
  **第一波は実行して分母から除外**（既定の作法）
- **回帰**: ヒビを含まない行が ±0.0 であること

### 4-3. ローカル台（Q0-3 で3行しか無かった場合）

**4台**。既存の駒だけで組み、新しい数値の駒は作らない。

| 台 | 目的 | 構成の条件 |
|---|---|---|
| 変換率が高い | ウロが読む | ヒビ ＋ ウロ ＋ 死軸 |
| 変換率が低い | 破片が素通りする側 | ヒビ ＋ 破片を読まない駒4枚 |
| ガルド同席 | §1-5 の切り分け | ヒビ ＋ ガルド ＋ 範囲の厚い波 |
| ヒビ単騎 | 供給そのものの測定 | ヒビ ＋ 何も読まない駒4枚 |

**台は `Presets` に置かず、診断のコード内に閉じる**（`compare` 61行を汚さない）。

## 5. 採否の線

> **強度のノブの決め方と、採否の線を別々の集合から引かない**（第135・136期の則）。
> `SelfCostPerTurn` を決めた集合と採否を判定する集合を**同じにすること**。

### 採用の条件（全部満たすこと）

1. **物差しを超える**: `ShatterSoaked / 戦` が **ヒビの 被弾/戦 を上回る**。
   これがこの期に立てる一般則の最初の適用例になる
   > ある駒が編成に加わる価値は、少なくともその駒が受ける被弾を上回らなければならない。
2. **特異性**: ヒビを含む行が動き、含まない行が ±0.0
3. **鍵の入れ替えが効いている**: `Turn` が `Passive` を上回るのが
   **「範囲の薄い波・薄い台」で特に大きい**こと。
   ここが逆（範囲の厚いところでだけ伸びる）なら、鍵ではなく単に供給量を増やしただけ

### 不採用でも残置する

`ShatterRule` は**削除せず `Passive` 既定のまま残す**（測って採らなかった機構は対照として残置、の規約）。
逆位・まどろみ・戦斧兵ほかと同じ扱い。

## 6. この期では決めないこと
