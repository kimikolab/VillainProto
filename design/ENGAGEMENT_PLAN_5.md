## 0. 出発点

第4期で「1波 ≒ 1部隊」の等価交換が確定した。接尾列（README の表）は第2波以降ほぼ全編成 1.00 で、**波を1つ抜くと部隊が丸ごと尽きる**。消耗の側から言い換えるとこうなる。

- 第一波の代金は約 25%（入場戦力 100% → 60〜88%）
- 第二〜五波の代金は約 50〜70%
- 波を勝ち抜く閾値も約 50%

つまり部隊の容量は「波の代金 1.5 個分」しかない。逆しま改が `[1..5]` で 2.00 に届くのは**第一波が安いから**であって、第二波以降の強さではない。**編成の強さが突破数に効く経路が「第一波が安い」ことしか無い。**

### この作業の狙い

**波の代金に差を作る。** ただし差の付け方は2種類あり、**両方要る**ことを最初に明示しておく。

- **波間の差**: 安い波と高い波を混ぜる。強い編成は安い波を連続で抜き、弱い編成はどこでも1つ。これで投入部隊数の配分に意味が出る
- **編成間の差（こちらが本命）**: 同じ波でも、編成によって代金が違うこと。数だけ多い雑兵は範囲攻撃の編成には安く単体攻撃の編成には高い。少数高HPの精鋭はその逆。**代金が全編成で同じ波は、いくら安くしても配分判断を生まない**（それが今の第二〜五波の状態）

ポン氏の意図する流れは **数だけ多い雑兵 → 雑兵（第一波より少し面倒）→ 精鋭部隊あるいはボス**。これは上の「編成間の差」を作る形として素直で、範囲有利 → 中間 → 単体有利、というコストの向きの反転が自然に入る。

## 2. Phase M — 波の代金を測る診断 `cost`

```
dotnet run --project BattleSim -c Release 0 cost [絞り込み]
```

診断モード。**`docs/` には出さない**（`seats` / `handoff` と同じ扱い）。

### 2-1. 測ること

**無傷の1部隊が、その波「だけ」と戦ったとき何を払うか。** 接尾列ではなく単独列 `[i..i]`（1波だけの部隊列）を使う。会戦として組む必要は無く、`BattleEngine.Run` を直接呼べばよい。

編成 × 波の表を2枚。seed 0..199。

**代金の表**（勝った試行だけを集計。負けた試行は代金が定義できない）

| 編成 | 第1波 | 第2波 | 第3波 | 第4波 | 第5波 |
|---|---|---|---|---|---|

セル形式: `{勝率}% / 残{体数:F1} {残HP%}` — 例 `100% / 残4.2 78%`

- 残 HP% の分母は**編成の定義上の総最大HP**（`engage` の入場戦力と同じ判断。生存駒だけを分母にすると全快1体が 100% に化ける）
- **代金 = 100% − 残HP%**。表には残存を出し、読み方の説明で代金に言い換える

**代金のばらつきの表**（この作業の本命）

| 波 | 勝率の中央値 | 代金の平均 | 代金の最小（編成名） | 代金の最大（編成名） | **代金の標準偏差** |
|---|--:|--:|--:|--:|--:|

**標準偏差が要点。** 波間の差は平均で、編成間の差は標準偏差で見る。既存5波はここが一律に小さい（＝どの編成にも同じ値段）と予想される。**そうなっていれば、この作業の目的が数字で裏付けられる。**

### 2-2. 検算

第1波の代金の平均が、`docs/engage.md` 順路の「第2戦の入場戦力」の平均とおおむね一致すること（順路の第1戦は第1波単独と同じ状況なので、残存も一致するはず）。**大きくずれたら止まって報告する**——`CarryOver` が残存に何かしている可能性がある。

### 2-3. 受け入れ条件

- `compare` / `chain` / `pulse` / `ablate` / `dump` / `engage` / `seats` / `handoff` の差分 **ゼロ**
- 2-2 の検算に言及すること（一致した / ずれた、数字で）
- 既存5波の代金の標準偏差を報告に貼る

## 3. Phase N — 勾配のある部隊列の候補

### 3-1. 設計の枠

3波1列（地点サイズ）。役割は固定、中身が候補。

| 位置 | 役割 | 代金の狙い | 有利になってほしい編成 |
|---|---|---|---|
| 第1波 | 数だけ多い雑兵 | **安い（20〜30%）** | 範囲攻撃（薙ぎ・全体）を持つ編成 |
| 第2波 | 雑兵（第1波より少し面倒） | **中（35〜50%）** | 特に偏らせない |
| 第3波 | 精鋭部隊 / ボス | **高い（50〜70%）** | 単体火力・積み上げ系 |

**3波の代金の合計が 100% を明確に超えること。** 超えなければ1部隊で全抜きできてしまい、部隊数の判断がまた消える。逆に合計が 200% を超えると2部隊でも抜けず、第2期の再来になる。**狙いは 110〜150%**。

### 3-2. 守る制約（既存のステージ定義のコメントから）

- 盤面は6枠（前3・中1・後2）。**1波あたり最大6体**
- **貫きは1波に1枚まで。** 2枚置くと後列に支援を置く編成が全滅する
- **全体攻撃は1波に1枚まで。** 2枚置くと支援型の駒が編成から消える
- `AttackPattern` を追加しない（4つまでの絶対ルール）
- 断罪の担い手は1体だと反撃編成に潰され、3体だと逆の崖になる（第五波の知見）。**新しい波に断罪を入れるなら2体**。入れないほうが素直
- **新しい `UnitDef` は新しい Id で追加してよい**（`EnemyCatalog` に足す）。既存の def は数値も含めて触らない。未使用の `Champion`（聖騎士長 130/22/9・処刑）は「第六波以降の素材」として置かれているので、第3波の候補に使える

### 3-3. 候補の出し方

**各位置につき 2〜3 案**を組み、Phase M の `cost` にかける。診断モード `gradient` を足すか、`cost` に「候補列も測る」引数を足すかは実装者判断でよい。**`EnemyCatalog.Columns` には足さない。**

候補を組むときの指針:

- **第1波（安い・範囲有利）**: 個体を弱くして数を増やす。5〜6体。HP 30 前後・攻撃 7〜9 の新 def が要るはず。**代金が範囲持ちと単体持ちで割れること**が成功条件。割れなければ「ただ安いだけの波」で、平均は下がるが標準偏差が上がらない
- **第2波（中間）**: 既存の第一波・第二波の中間。4体前後。極端な役割を入れない
- **第3波（高い・単体有利）**: 少数高HP。2〜3体。`Champion` / `Warden` が素材。**回復役を入れるかどうかで性格が大きく変わる**ので、司祭入り・司祭なしの両方を候補にすること

### 3-4. 報告の形

**採用は決めない。順位付きで提示する。** 各候補について:

- 代金の平均（波間の差が狙い通りか）
- **代金の標準偏差（編成間の差が出たか）**
- 代金が最も安い編成・最も高い編成の名前。**第1波では範囲持ちが安く、第3波では単体火力が安くなっているか**（狙いの向きが実現しているか）
- 勝率が 0% になる編成があるか（あってよいが、何編成かは知りたい）

そのうえで、**3波の組み合わせとして推奨する1本**を、理由付きで挙げる。合計代金が 3-1 の 110〜150% に入るか、期待突破数はどうなるか（3波列で1部隊・2部隊を測る）まで出す。

### 3-5. 受け入れ条件

- `compare` ほか既存の生成物すべて差分 **ゼロ**（新しい `UnitDef` を足しても、既存のステージが参照しなければ何も動かない。**動いたら既存 def を触っている**）
- `EnemyCatalog.Columns` が変わっていないこと
- 候補の全数値（def の HP / 攻撃 / 速度 / パターン / 配置）が、報告かコード中のコメントで読めること

「未解決の課題」:

- 勾配列の候補と、採用が保留であること。ポン氏の判断待ちと明記
- 第3期・第4期からの持ち越し（D5 の再検討 / 部隊戦間の回復 / 1波≒1部隊）はそのまま残す

### 4.2 報告してほしいこと

1. **既存5波の代金の表と標準偏差。** 予想（どの波もどの編成にも同じ値段）は当たったか
2. **第1波が安い理由**は何か。体数が少ないからか、攻撃力が低いからか。`cost` の数字から言えること（推測は推測と明記）
3. **候補の順位と、推奨する3波の組み合わせ1本。** 3-4 の項目すべてに数字で
4. **第1波の候補で、範囲持ちと単体持ちの代金が実際に割れたか。** 割れなければ、なぜ割れなかったか
5. **推奨列での期待突破数（1部隊・2部隊）。** 第4期の「+1.00 一律」が崩れたか。**崩れていなければ、それがこの方向の限界を示す重要な結果**なので、そう書く

## 5. 作業ルール

1. Phase M → N → O の順。**フェーズを跨いで1コミットにしない**（O は文書のみ）
2. コミットメッセージに「動いた docs/ の行」を書く。動いていないなら「compare 差分ゼロ」と明記
3. コード・コメント・ログは日本語。既存の文体（**却下した案とその理由も書く**）に揃える。新しい `UnitDef` には**なぜその数値なのかをコメントで残す**（既存の敵 def はすべてそうなっている）
4. CONTRIBUTING.md のチェックリストを通す
5. 長時間ジョブは前景で待ち切る。`layout` は走らせない
6. **採用を決めない。** 推奨は出してよいが、`Columns` への追加も `Stages` の変更もしない
7. 以下を見つけたら**実装前に止まって報告する**:
   - Phase M の検算（2-2）が大きくずれた場合
   - 既存5波の代金の標準偏差が既に大きかった場合（＝前提が外れている。**その場合この作業の設計自体を見直す必要があるので、候補作りに進まず報告する**）
   - 候補を組むうえで 3-2 の制約と狙いが両立しない場合（例: 6体でも代金が安くならない）
