## 0. この期の主題

**隣接を「量」ではなく「誰がいるか」で読む駒を1枚作り、席が編成で動くかを測る。**

第45期の調査の結論は次の3点だった。

- **Q1**: 席に値段はあるが、**値段の95%は「破滅的な置き方の回避」**。
  幅（1位−最下位）の中央値 44.35pt に対し、1位−5位は 2.15pt、1位−現行は 1.50pt。
  しかも1位は seed 帯を変えると48行中28行で入れ替わる
- **Q2**: **隣接は判断を生んでいない。むしろ消している。**
  3値（前角/中央/後角）の最頻率は 隣接 85% 対 対照 65%。
  コスト型（ボルグ/リィカ/スィド）は全行で角、利得型（カド）は中央率82%。
  **席が編成で動いたのは隣接を読まない駒のほう**（ガン44%・ウツ40%・ノノ50%）
- **Q3**: 原因は**隣接を単調な量として読むこと**。次数が {2,4} の2値なのは増幅器。
  ロスターで隣接を非単調に読む唯一の1枚（ヒサ・囃し立て）だけが対照と同水準（62% 対 63.5%）

**盤面の次数分布を変えるより、特性側を試すほうが桁違いに安い。** ヒサの n=1 を n=2 にする。

## 1. この期から変える作法（2件）

第45期の結果を受けて、以下を**この期から標準にする**。

### 作法1: 新しい駒は `CompareBuilds()` に**最低2行**で入れる

第41〜43期のハネ・ウケ・ワタは3枚とも1行しかなく、`reseat` は編成内の席しか振らないので、
**「同じ駒が編成によって別の席に行くか」は一度も測られていなかった。**
それにもかかわらず3期連続の傾向として扱われた。**1行では席の分散は測れない。**

2行目は相方を変えるだけの安い形でよい。予算壁（払い出しが4枠で 20% に潰れる）に
当たらない範囲で組むこと。

### 作法2: 配置の採否閾値 **+2.0pt を使わない**

第41〜43期の指示書は「`reseat` で配置を決め、+2.0pt で `confirm`」と書いていたが、
**1位−5位の幅が 2.15pt** なので、**ほぼノイズを閾値にしていた。**

代わりに以下で判定する。

- **現行の配置が `reseat` の上位5通りに入っているなら、配置換えをしない**
- 入っていない場合のみ、上位5通りの中央値と現行の差を `confirm`（seed 200..599）で確認する
- **`reseat` の1位を採否の根拠にしない**（seed 帯で28/48が入れ替わる）

**Phase 0 でこの閾値を数字として決め直すこと**（§2-2）。

## 3. 実装

### 3-1. 特性 `TraitId.Overbear`（驕り）

```
Overbear,    // 驕り: 隣の味方を見下して腕を鈍らせ、隣が全員自分より弱くなったとき本気を出す
             // （1つの動作の表と裏。削るのは常時、報われるのは条件を満たしたときだけ）
```

**プラス・マイナスのどちらのブロックにも入れない。**

#### マイナス側 —— 常時

`OnTurnStart` で、**隣接する生存味方全員**に対して
`ctx.Dull(ally, Drain, DullRoute.Overbear)` を呼ぶ。

- **`ctx.Dull` を必ず通すこと。** 直接 `AtkBonus` を引くと、
  ウケの横取り（アーマー化）もワタの転嫁（敵へ流す）も走らない。
  **弱体軸への供給になることがこの駒の価値の半分**
- **`DullRoute` に `Overbear` を足す**
- `AcceptsSupport` の判定は**呼び出し側でしない**（第44期の誹りと揃える）。
  既存経路と不揃いになるが、揃えると既存48行が動く。**どう実装したかを報告書の表に明記**

#### プラス側 —— 条件を満たしたときだけ

`ModifyAttack` で、**隣接する生存味方が全員、自分より `CurrentAttack` が低いとき**、
攻撃力を2倍にする。

- 隣接する生存味方が **0 人のときは条件を満たさない**（誰も見下していないので発揮しない）。
  これを満たすと角に置くだけで無条件2倍になり、二択に戻る
- 条件付き2倍は `SniperTrait`（後衛特化）に前例がある。**同じ形で書くこと**

#### なぜこの形が非単調なのか（実装者向けの設計意図）

**隣接数が増えるほど条件は厳しくなる**（AND 条件なので）。
中央（隣4人）は削る量が多い代わりに条件の成立が遅く、角（隣2人）は逆。
**さらに「隣が誰か」で成立時刻が変わる**——ドルガ（攻38）の隣なら長くかかり、
クビ（攻3）の隣なら即座に成立する。

**第45期が「隣接を単調な量として読むと二択に潰れる」と結論したので、
この期の主眼は「非単調にすれば席が編成で動くか」の1点である。**
勝率はその結果に過ぎない。

### 3-2. 強度のノブ `OverbearRule`

```
public readonly record struct OverbearRule(int Drain)
{
    public static OverbearRule Default => new(2);
}
```

- 掃引は **1 / 2 / 3**
- `Drain = 0` は「削らないので条件が永遠に成立しない」＝**プラス側だけを切る対照**になる
- `BattleEngine.Run` の引数に足す（既存の各 `Rule` と同型）。**static のノブは置かない**

### 3-3. 駒 `UnitCatalog.Ogo`（驕りのオゴ）

```
Id = "ogo", Name = "驕りのオゴ", MaxHp = 62, Attack = 12, Speed = 5,
Traits = { TraitId.Overbear }, Pattern = AttackPattern.Single
PlusText  = "隣の味方が全員自分より弱いあいだ、攻撃力が2倍になる"
MinusText = "毎ターン隣の味方の腕を鈍らせる。隣に誰もいなければ本気も出せない"
Flavor    = "自分より下がいないと力が出ない。だから下を作ることにした。"
```

数値は探索段階の初期値。**掃引の対象は `Drain` だけ**で、HP・攻・速は振らない。

### 3-4. compare への追加 —— **2行**（作法1）

```
("驕り (オゴ×◯)", ...)      ← 条件が早く成立する台（攻撃力の低い駒を隣に置く）
("驕り改 (オゴ×◯)", ...)    ← 条件が遅く成立する台（攻撃力の高い駒を含む）
```

- **2行の相方は Phase 0-4 の攻撃力分布から選ぶこと。**
  1行目は成立が早い台、2行目は遅い台にして、**成立時刻の違いが席の選び方に出るか**を見る
- **弱体の読み手（ウツ / ウケ / ワタ）を含む版を最低1つ試すこと。**
  オゴは `Dull` の供給源なので、読み手と組めば「削る」がそのまま収入になる。
  ただし**読み手を隣に置くと条件が成立しにくくなる**（ウツは弱体で攻撃力が上がるため、
  削るほど条件から遠ざかる）——**この自己矛盾が起きるかを必ず確認して報告すること**
- 配置は §1 の作法2 で決める。**`reseat` の1位を採否の根拠にしない**

**既存48行は1つも触らない。**

## 4. 診断モード `overbear`

`BattleSim` に追加する。**出力は `docs/` に置かない**。
`CompareBuilds()` / `Stages` / `Columns` を触らないこと。

| 列 | 中身 |
|---|---|
| 削り | 撒いた総量/戦・**削った相手の内訳** |
| 成立率 | 条件を満たしていたターン数 / 全ターン数 |
| **成立時刻** | **条件が初めて成立したターン**（成立しなかった試行は別途カウント） |
| 2倍 | 2倍が乗った攻撃回数/戦 |
| 横取り | ウケ / ワタ が横取りした量/戦（＝削りが資産に変わった量） |
| 素通り | 読み手に届かずただの損になった量/戦 |
| 逆行 | **ウツを隣に置いた場合に、削りが条件成立を遠ざけた量**（§3-4 の自己矛盾） |
| 攻ゼロ | 味方の `CurrentAttack` が 0 になった回数/戦・誰が |

**「成立時刻」がこの期の核心。** 席（隣接数）と相方（隣の攻撃力）の両方で変わるはずで、
**変わらなければ非単調にした意味が無い。**

**陽性対照を必ず置く**: `OverbearRule(0)`（削らない＝条件が成立しない）と、
オゴを外した同じ編成の2本。

**発火しなかったことは盤面の値に痕跡を残さない**ので、ログか `Events` から数えること。

### 掃引（必須の 1〜5 を通ってから）

`Drain` を **1 / 2 / 3** の3点で測る。基準として `OverbearRule(0)` の1本を置く。

**見るのは勝率ではなく「成立時刻」と「席の分散」。**
第41期の掃引は「比が全点で 2.30 で動かない＝ノブは強度しか変えず性質を変えない」を示した。
**`Drain` は成立時刻を直接動かすノブなので、席の分散も動くはず。動かなければ
非単調化が効いていない証拠になる。**

## 7. 実装上の注意（既知の落とし穴）

1. **`ctx.Dull` を必ず通す。** 直接 `AtkBonus` を引くと弱体軸への供給にならない
2. **隣接する生存味方が 0 人のときは条件を満たさないこと**（§3-1）。
   ここを満たすと角に置くだけで無条件2倍になり、第45期が指摘した二択に戻る
3. **`ModifyAttack` は毎回評価される。** 条件は戦闘中に成立したり不成立に戻ったりする
   （味方が倒れて隣接が減る、ウツが育つ）。**フラグで固定しないこと**——
   非単調性はこの揺れから来る
4. **ウツとの自己矛盾は潰さない。** 削るほどウツが強くなって条件から遠ざかるのは
   **設計として正しい**（同じ通貨の供給者と読み手が隣り合えない）。
   バグとして修正せず、**測って記録する**
5. **`ModifyAttack` の2倍と `PerverseTrait` の3倍が同一駒に乗らないこと。**
   オゴは `Perverse` を持たないので現状は問題ないが、
   **乗算フラグを増やさない**（ロスターで乗算は熾火の1つだけ）
6. **乱数列はずれる。** `Dull` の中の横取り判定で `PickOne` が走ると
   候補2個以上で `Roll` を消費する。帰属は `OverbearRule(0)` かオゴ抜きの対照で取る
7. **召喚枠（スロット5〜8）の扱いを明記する。** 隣接表に召喚枠が含まれるので
   削りの対象にも条件の判定にも入る。**含めたかどうかを報告書に書く**。推奨は「含める」
8. **長時間ジョブはフォアグラウンドで1ツール呼び出し内に収める。** 背景に回さない。
   第45期の `seats2` は 8.4秒/行だったので、2行なら十分収まる
