## 0. なぜこれをやるか

初回計測（`docs/engage.md`）は「波が易しすぎる」を反転させたが、**反転した先が均一すぎる**。

- 全31編成が突破 0%。3部隊目に届いたのは移動改の 3/200 のみ
- 期待突破数のレンジは 1.00〜2.00 で、上限 2.00 に4編成が張り付いている
- 逆しま改は 200/200 が突破ちょうど2

つまり現在の `engage` は実質「第2波を残存多く抜けられるか」という一問しか測れていない。序列としての情報量は独立5戦より減っている可能性がある。**これは係数の崖と同じ形**（README の原則: 二値になったら数値でなく構造を疑う）。

原因の候補は2つあり、まだ切り分けられていない。

- **(A) 第三波が単発で重い** — 勇者候補 95/20 + 巡礼騎士 75/15 ×2 + 戦斧兵 + 狙撃手
- **(B) 第三波に着く時点の残存戦力が全編成一律に低い** — 消耗（HP非回復）が共通の壁

README は (B) と書いているが、**それを示す数字はまだ無い**。この作業でまず (A)/(B) を切り分け（Phase E）、次に「5波1本」という部隊列の形そのものを変数にする（Phase F）。

**この作業では数値を一切調整しない。** 特性・ユニット・ステージの数値、`NecroTrait` の減衰量（T2）、境界回復（T4）はすべて据え置き。壁の原因が分かるまで触ると崖を掘りに行くことになる。

## 2. Phase E — 入場戦力の計測

### 2.1 何が分かればよいか

「第3戦の開始時点で、味方部隊はどれだけ残っているか」。全編成が一律に低ければ (B)、健在なのに落ちるなら (A)。

### 2.2 実装

`EngagementResult` に、**verbose に関係なく**積む集計を足す。`Openings` は verbose 専用（`docs` 生成は `verbose: false`）なので使えない。

```csharp
/// <summary>部隊戦に入る時点の味方戦力。verbose に関係なく積む（勝率計測から読むため）。</summary>
public sealed record SquadEntry(
    int Alive,        // 生存数
    int HpSum,        // 現在HPの合計
    int MaxHpSum,     // 現在の最大HPの合計（継ぎ接ぎの損耗が乗った値）
    int DefMaxHpSum); // 定義上の最大HPの合計（損耗前）
```

`EngagementResult` に追加:

```csharp
/// <summary>各 Battle の開始時点の味方戦力。Battles と同じ長さ。verbose=false でも積む。</summary>
public required IReadOnlyList<SquadEntry> PlayerEntries { get; init; }

/// <summary>同じく敵側。持ち越された敵部隊がどれだけ削れていたかを見る。</summary>
public required IReadOnlyList<SquadEntry> EnemyEntries { get; init; }
```

**積む場所**: `EngagementEngine.Run` の中で、各 `BattleEngine.Run` を呼ぶ**直前**に、その戦闘に入る `UnitState` 群から計算する（`Openings` を作っているのと同じ位置。`Openings` は verbose 判定の中、こちらは外）。

- `MaxHpSum` と `DefMaxHpSum` を分けるのは、**継ぎ接ぎ（ヴェル）の最大HP半減で `Hp/MaxHp` 比が健康に見える**ため。ヴェルは 46→11 まで削れるので、比率だけ見ると「満タン」に化ける。分母は定義値（`DefMaxHpSum`）を使う。
- **盤面を一切触らないこと。** 読むだけ。受け入れ条件は `compare` 差分ゼロ。

### 2.3 出力

`docs/engage.md` に第2の表を足す。既存の突破分布の表はそのまま残す。

```
### 入場戦力（味方）

各部隊戦に入る時点の味方の生存数と HP（定義上の総最大HPに対する割合）。
到達しなかった試行は分母から外す（到達した試行だけの平均）。**到達率も併記する。**

| 編成 | 第1戦 | 第2戦 | 第3戦 | 第4戦 | 第5戦 |
|---|---|---|---|---|---|
| 逆しま改 (クビ×ウツ) | 5体 100% (200/200) | 3.8体 61% (200/200) | 2.1体 28% (200/200) | — (0/200) | — (0/200) |
```

セル形式: `{生存数:F1}体 {HpSum/DefMaxHpSum:F0}% ({到達試行}/{全試行})`。到達 0 なら `— (0/200)`。

**到達率の併記が要点。** 平均だけだと「第3戦に着いた少数の強い試行」で数字が持ち上がり、壁の位置を見誤る。

敵側（`EnemyEntries`）は**別表にせず**、味方表の下に1行の要約で足す:

```
持ち越された敵部隊が削れていた割合の平均（全編成・全試行）: 第2戦 0%（新規投入のため）…
```

味方1部隊しか投入していない現状では敵は毎回新規投入なので、`EnemyEntries` は常に 100% になるはず。**そうなっていなければ実装がおかしい**ので、検算として1行出す。

### 2.4 判定（Phase G で報告する）

| 観測 | 結論 |
|---|---|
| 第3戦入場が全編成 40% 未満 | **(B) 消耗が壁。** 部隊列の長さか回復の設計を触る話になる |
| 第3戦入場が 70% 以上あるのに突破が止まる | **(A) 第三波が重い。** 部隊列の順序・構成を触る話になる |
| 編成ごとに大きく割れる | どちらでもなく、既に序列として機能している。壁は問題でない |

### 2.5 受け入れ条件

- `compare` / `chain` / `pulse` / `ablate` / `dump` の差分 **ゼロ**（純粋な追加）
- `EngagementEngine.Run` の決定性が保たれている（同じ引数2回で `PlayerEntries` が一致）
- `docs/engage.md` に入場戦力の表が出て、コミットに含まれている
- 敵側の検算行が全て 100% になっている（味方1部隊のとき）

## 3. Phase F — 部隊列の複数化

### 3.1 なぜ

既存5波は「独立した5つの難度段階」として設計されたもので、**1本の会戦として設計されていない**。現在の `EngagementColumn` はそれを機械的に並べただけ。「5波を1本で全抜き」が誰にもできないのは、部隊列の設計が無いことの結果であって、編成が弱いことの証拠ではない。

コンセプトメモ §7 では、マップ上の1地点は敵1〜3部隊。**そもそも全抜きの対象は5部隊ではない。**

### 3.2 実装

`EnemyCatalog` に名前付きの列を持たせる。**`Stages` は1文字も触らない。**

```csharp
public sealed record Column(string Name, string Note, IReadOnlyList<Formation> Squads);

public static IReadOnlyList<Column> Columns { get; } = new[]
{
    // 既存5波をそのまま並べたもの。初回計測（2026-08-25）の基準列。
    new Column("順路", "既存5波の並び順。第1期の基準",
        Stages.Select(s => s.Enemy).ToList()),

    // 逆順。**第1削りを情報のある列にするための列。**
    // 順路では第一波が全編成必勝で `第1削り` が一律 100% になり、特攻隊（勝てないが削る編成）を
    // 判別できなかった（README 未解決の課題）。敵を新造せず、並べ替えだけで測定条件を作る。
    new Column("逆順", "強い波が先頭。特攻隊（勝てないが削る編成）の測定用",
        Stages.Reverse().Select(s => s.Enemy).ToList()),

    // 3部隊。コンセプト上、マップ上の1地点は敵1〜3部隊（design/concept_wave_engagement.md §7）。
    // 順路の先頭3つを切り出す——**長さだけを変数にする**ため、中身も順序も順路と同じにしてある。
    new Column("地点", "順路の先頭3波。1地点の想定サイズ",
        Stages.Take(3).Select(s => s.Enemy).ToList()),
};
```

`EngagementColumn`（既存プロパティ）は `Columns[0].Squads` を返すよう書き換える。**削除しない**（GodotApp が使っている）。

### 3.3 BattleSim

`engage` は**3本すべてを1回の実行で測り、1つの `docs/engage.md` に列ごとの節として出す**。コマンドを増やさない（`CONTRIBUTING.md` の手順を増やさないため）。

```
dotnet run --project BattleSim -c Release 0 engage [絞り込み] > docs/engage.md
```

出力構成:

```
# 会戦
（共通の説明。持ち越すもの／消えるもの／各列の読み方）

## 順路 — 既存5波の並び順
### 突破分布
### 入場戦力（味方）

## 逆順 — 強い波が先頭
### 突破分布
### 入場戦力（味方）

## 地点 — 順路の先頭3波
### 突破分布
### 入場戦力（味方）
```

実装上の注意:

- **独立積は列ごとに測り直さない。** 独立積は「各波の独立勝率の積」なので、順路と逆順は**同じ値になる**（積は順序に依らない）。波ごとの独立勝率を1回だけ測ってキャッシュし、列ごとに必要な波の積を取る。順路と逆順で違う数字が出たら実装がおかしい（検算として使える）。
- 実行時間: 初回が約6秒。列3本＋入場戦力で 20 秒程度を見込む。`compare` より軽いので前景で待ち切れる。
- `engage2`（同一編成2部隊）も同じ3列に対応させる。ただし `docs/` には出さない現状の扱いを維持（診断用）。時間がかかるなら**順路と地点の2本だけ**でよい。

### 3.4 受け入れ条件

- `compare` / `chain` / `pulse` / `ablate` / `dump` の差分 **ゼロ**
- 順路の突破分布が、Phase E 適用後の値と**完全一致**すること（列の抽象化で挙動が変わっていないことの検算。`EngagementColumn` = `Columns[0].Squads` なので一致するはず）
- 順路と逆順の独立積が編成ごとに一致していること
- `docs/engage.md` に3節が出ている
- `CLAUDE.md` / `CONTRIBUTING.md` のコマンド一覧・生成物リストの記述が実態と合っている（`engage` の説明に「3本の列を測る」を足す）

## 4. Phase G — 記録と報告

### 4.1 README に書くこと

「検証で分かったこと」の会戦の項に追記する。既存4項は消さず、**訂正が必要になったら訂正と分かる形で**書く（例: 「第1期では『全編成が第3波で止まる』と記録したが、地点列（3部隊）では〜」）。

- (A)/(B) の判定と、その根拠になった入場戦力の数字
- 地点列（3部隊）での突破率。**ここで初めて「全抜きできる編成」が出るはず**。出たなら、それが編成の新しい序列になる
- 逆順列での第1削り。特攻隊が判別できるようになったか。突破 0 なのに削りが高い編成があるか
- 「未解決の課題」の**特攻隊の項を解決済みに移す**（逆順列で測れるようになったため）

### 4.2 報告してほしいこと（実装ではなく分析）

1. **(A) か (B) か。** §2.4 の判定表のどれに当たったか、数字を引いて
2. **地点列（3部隊）で突破率が意味のある分布になったか。** 0%〜100% に散っていれば、会戦の序列はこの長さで機能する。ここでも全員 0% や全員 100% なら、長さは原因ではない
3. **逆順列で特攻隊が見えたか。** 第1削りが編成ごとに割れたか。突破数と削りの順位が食い違う編成があるか（＝勝てないが価値のある編成）
4. **順路・逆順・地点で編成の序列がどれだけ入れ替わるか。** 大きく入れ替わるなら「部隊列ごとに最適な編成が違う」ことになり、複数部隊制の狙い（コンセプト §6「最強の5人を作るゲームにしない」）がシステム側で成立している証拠になる。ほぼ同じ順位なら、列を増やしても編成の判断は増えていない

### 4.3 GodotApp について

この作業では**触らない**。`EngagementColumn` が `Columns[0].Squads` を返す限り、Godot は現状のまま動く（ビルドが通ることだけ確認する）。列を選べる UI は、Phase G の報告で「どの列を標準にするか」を決めてから別作業で入れる。

## 5. 作業ルール

1. Phase E → F → G の順。**フェーズを跨いで1コミットにしない**（G は文書のみのコミット）
2. 各コミットメッセージに「動いた docs/ の行」を書く。動いていないなら「compare 差分ゼロ」と明記
3. コード・コメント・ログは日本語。既存の文体（**却下した案とその理由も書く**）に揃える
4. CONTRIBUTING.md のチェックリストを通す。特に:
   - `Trait` にインスタンスフィールドを足さない / 再入フラグを static に置かない
   - `LivingMembers` はスナップショットで使う
   - `BattleCore` に UI 参照を入れない
   - 純粋な追加なので `compare` 差分は**ゼロでなければならない**。1pt でも動いていたら集計のつもりで挙動を変えている
5. 長時間ジョブは前景で待ち切る。`layout` は走らせない（Slot 固定のため）
6. **数値を調整しない。** 壁が動かなくても、この作業では記録だけして Phase G の報告に書く
7. 以下を見つけたら**実装前に止まって報告する**:
   - `SquadEntry` を積む位置で、盤面に触れずには計算できない値があった場合
   - `Stages.Reverse()` で列を作ると、ステージ定義のコメントにある教育的意図（「範囲攻撃の存在をここで教える」等）と矛盾する副作用が出る場合
