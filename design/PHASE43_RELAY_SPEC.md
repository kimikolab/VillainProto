## 0. この期の主題

**弱体軸の三役目を作る。** 第42期で窓口 `ctx.Dull` と読み手2枚が揃った。

| 役 | 駒 | 弱体を何に変えるか | 誰が得をするか |
|---|---|---|---|
| 変換・攻 | 逆しまのウツ | **攻撃力**（下げ幅の3倍） | 自分だけ |
| 変換・防 | 引き受けのウケ | **アーマー**（下げ幅の `ArmorPerDull` 倍） | 自分だけ |
| **転嫁** | **渡しのワタ**（新規） | **敵の攻撃力** | **味方全体** |

前2枚は増幅がある代わりに受け手1体で閉じる。渡しは**増幅が無い代わりに味方全体に効く**。
傷軸で 抉り（+3/傷・維持）と 断ち（+5/傷・全消費）が別の順位を作ったのと同じ形を、弱体で作る。

**味方から敵へ状態を移す経路はロスターにゼロ。** 窓口 `Dull` が両陣営を通るように
作ってあるので、実装は「横取りして流し先を敵にする」だけで済む。

### この期に効いている制約（第40〜42期の実測から）

1. **新機構は2枠で成立させること。** 直近3期の新行のうち後半2波に届いたのは
   `分かち×逆しま (ドハ×ウツ)`（供給兼土台→読み手の2枠）だけで、
   3枠使った `突き返し` は第4/5波 2.0/0.0、`引き受け` は 0.5/0.5 で床に落ちている。
   **払い出しの枠数そのものが原因**なので、駒を強くしても解けない
2. **隣接を条件にする機構は、「隣に置きたい駒」を先に名指ししてから台を組むこと。**
   第42期の集約は排他が完全に立った（隣接 9.0→9.0 / 非隣接 20.8）が、
   **非隣接のほうが +9.1pt 強かった**ので、置き場所が一意に決まって判断が消えた。
   隣接がコストにしかならなかったのは、**隣に置く価値のある駒を先に決めていなかったから**
3. **効いた量で判断すること。** 第42期は「生成したアーマー」ではなく
   「実際に吸った量」を数えて死蔵率 2.5% を出した。渡しも同じで、
   **流した量ではなく「味方の被ダメージがいくら減ったか」で読む**

## 2. 実装

### 2-1. 特性 `TraitId.Relay`（渡し）

```
Relay,       // 渡し: 隣の味方が受ける攻撃力低下を引き受け、そのまま敵へ渡す。
             // ただし通り道になった自分の身が削れる（1つの動作の表と裏）
```

**プラス・マイナスのどちらのブロックにも入れない。**

#### 横取り

**`Bear`（集約）とまったく同じ条件**で横取りする。

- 対象が自分に隣接している生存味方であること
- 対象が自分自身なら横取りしない
- 対象が `Relay` 持ちなら横取りしない
- 候補が複数なら既存の `PickOne` の慣習に従う

**`Bear` と `Relay` が同時に候補になったときの優先順位を決めること。**
指示書の推奨は「両方を1つの候補プールに入れて `PickOne`」——
どちらが取るかが運になるのは望ましくないが、**優先順位を固定すると
片方が構造的に飢える**（第41期の「先に来る供給源だけが使われる」と同じ形）。
決めた側と理由を報告書に書くこと。

#### 転嫁

横取りした量 `a` に対して、`a × TransferPercent / 100` を
**敵陣で `CurrentAttack` が最も高い生存駒**へ `ctx.Dull` で流す。

- **流し先は決定的に選ぶ。** 乱数で選ぶと何に課金したのか分離できない
- **最高攻撃力を選ぶことで自己分散する**——削れば次は別の敵が最高になるので、
  1体を 0 まで削り切る前に対象が移る。崖を避けるための選び方でもある
- 同値が並んだ場合のみ `PickOne`
- 流す先で再び `Dull` を通るので、**敵側に `Bear` / `Relay` 持ちがいれば
  そちらの横取りが走る**。現状は敵に誰もいないので発火しないが、**再入ガードを入れておく**
  （敵側に渡しを置いた瞬間に無限往復する）

#### 代金

`RelayTrait.HpCostPerDull = 2`（定数。ノブにしない）。

横取りした量 `a` に対して `a × HpCostPerDull` のダメージを自分に与える。

- **`ApplyDamage` を通すこと**（直接HPを引かない）。庇う・分かち・巨躯・後備え・棘守りが
  割り込むので、**「代金を誰かに肩代わりさせる」が編成の選択肢になる**
- ただし**意図した代金が効かなくなる**ので、`relay` 診断で
  **「ワタが実際に自分で払った割合」を必ず数えること**（§3）
- `isFriendlyFire: true` で通す（味方由来の damage として扱う）

**代金が構造的な歯止めになっている点に注意。** 供給の種類で桁が変わる。

| 供給 | 1回の量（目安） | 代金 |
|---|--:|--:|
| 分かちのなまり（被弾のたび・少量） | 1〜2 | 2〜4 |
| 萎縮（開戦時1回・隣接4体ぶんを横取りすると） | 〜36 | **〜72** |

ワタのHPは84なので、**萎縮と同居すると開幕で自壊する**。これは仕様
（可変コスト型）だが、そうなることを予測に書いてから測ること。

### 2-2. 強度のノブ `RelayRule`

```
public readonly record struct RelayRule(int TransferPercent)
{
    public static RelayRule Default => new(100);
}
```

- 掃引は **0 / 50 / 100**
- **`TransferPercent = 0` は「横取りするが流さない」＝ 弱体が消滅する。**
  これは**除去役**そのものなので、**転嫁と除去を1つのノブで比較できる**。
  対照であると同時に、それ自体が設計案の検算になっている
- `BattleEngine.Run` の引数に足す（既存の各 `Rule` と同型）。**static のノブは置かない**

### 2-3. 駒 `UnitCatalog.Wata`（渡しのワタ）

```
Id = "wata", Name = "渡しのワタ", MaxHp = 84, Attack = 8, Speed = 7,
Traits = { TraitId.Relay }, Pattern = AttackPattern.Single
PlusText  = "隣の味方が受ける攻撃力低下を引き受け、最も強い敵へそのまま渡す"
MinusText = "渡した分だけ自分の身が削れる。隣に誰もいなければ何も起きない"
Flavor    = "受け取った呪いを、そのまま向こうへ渡す。通り道の自分だけが削れていく。"
```

数値は探索段階の初期値。**掃引の対象は `TransferPercent` だけ**で、HP・攻・速は振らない。

### 2-4. compare への追加 —— **1行だけ**

```
("渡し (ワタ×ドハ)", ...)
```

- **2枠で組むこと**（供給兼土台の ドハ ＋ 転嫁の ワタ）。残り3枠は既存の土台
- **Phase 0-4 で名指しした駒（ドルガ想定）をワタの隣に置く台を必ず1つ試すこと。**
  これが「隣接が値段として機能するか」の検算になる。
  第42期の集約は隣に置く価値のある駒がいなかったので、隣接がコストにしかならなかった
- 配置は `reseat` で決める。**ワタは隣接次数が守備範囲なので中央（次数4）が上位に来るはず**だが、
  中央は代金も4体ぶん増える。**ウケ（中央が1位）と同じ向きに出るか逆に出るかを見ること**
- 配置換えを採るときの閾値は **+2.0pt**（seed 200..599・選定に使っていない帯で `confirm`）

**既存47行は1つも触らない。**

## 3. 診断モード `relay`

`BattleSim` に追加する。**出力は `docs/` に置かない**。
`CompareBuilds()` / `Stages` / `Columns` を触らないこと。

| 列 | 中身 |
|---|---|
| 横取り | ワタが引き受けた量/戦・**取られた相手の内訳** |
| 素通り | 隣接に誰もいなくて横取りできなかった量/戦 |
| 渡し | 敵へ流した量/戦・**流し先の内訳**（敵の名前ごと） |
| 最大流入 | **1回の `Dull` で流した最大量**（崖の検算・§5-4） |
| 攻ゼロ | **敵の `CurrentAttack` が 0 になった回数/戦**（崖の検算） |
| 代金 | ワタが負ったダメージ/戦 |
| **自弁率** | **そのうちワタ自身が実際に払った割合**（肩代わりされなかった分） |
| 効き | **味方全体の被ダメージが対照よりいくら減ったか**/戦 |
| 早逝 | ワタが倒れたターン（倒れた試行の平均） |

**「渡し」と「効き」を分けて数えること。** 第42期が「生成したアーマー」ではなく
「実際に吸った量」で判断して死蔵率 2.5% を出したのと同じ理由で、
**流した量は成果ではない**。敵の攻撃力を下げても、その敵が既に死んでいたり
もともと殴らない駒だったりすれば効いていない。

**「自弁率」も必須。** 代金を `ApplyDamage` で払う以上、
前列の肩代わり役が代わりに払う。**過去に同型の機構で「代償8のうち本人が払ったのは1」
という実測がある。** 最初から数えること。

**陽性対照を必ず置く**: `RelayRule(0)`（横取りするが流さない）と、
ワタを外した同じ編成の2本。

**発火しなかったことは盤面の値に痕跡を残さない**ので、ログか `Events` から数えること。

## 4. 予測（実装の前に書き、報告書に当否を載せる）

**軸の名前ではなく、窓口を通る駒の在庫で書くこと。** 第41期は3件、第42期は死蔵率を外している。
どちらも「窓口を通る量が定常状態でどうなるか」の数え損ねだった。

実装の前に以下を書き出す。

1. **`渡し (ワタ×ドハ)` でワタが1戦に横取りする総量**を計算する。
   ドハのなまりは `肩代わり量 / 4` の切り捨てで、肩代わり総量はドハのHP104が上限。
   第42期の実測では `分かち×逆しま` のウツが 9.0 → 25.8 まで育った
   （＝弱体の総量は `(25.8 - 9) / 3` ≒ 5.6）。**同じ台なら同じ量が流れるはず**
2. **その量を最高攻撃力の敵に流したとき、敵の攻撃力が何%下がるか**を波ごとに書く
3. **ワタが払う代金の総量**（横取り量 × 2）と、**ワタのHP84に対する比**
4. **萎縮（クビ）と同居した場合に開幕で自壊するか**。同居版を1つ測ること
5. **`reseat` でワタの席が中央に来るか角に来るか。** 守備範囲（横取りできる量）と
   代金（払うHP）が**同じ隣接次数から出る**ので、ウケ（中央1位）と同じ向きに出るとは限らない。
   **どちらに出るかを先に予測して理由を書く**
6. **敵の攻撃力が 0 になる回数**。0 なら崖の心配は無い。1回でも出たら §5-4 を見る
7. **`TransferPercent = 0`（除去）と 100（転嫁）でどちらが強いか。**
   除去は味方の攻撃力を守るだけ、転嫁は敵の攻撃力も下げる。
   **転嫁が強くて当たり前に見えるが、除去は代金の意味が変わる**
   （流さないなら通り道になる必要が無い）ので、**同じ代金を払う設計であることを
   踏まえて予測すること**

**予測を外したら、外した理由を報告書に書く。** 当てることが目的ではない。

13. 固有の勝者・敗者の増減。**厳密版（=100 / =0）と緩い版（90/10）のどちらを使ったか毎回書く**

## 6. 実装上の注意（既知の落とし穴）

1. **再入ガードを入れる。** 転嫁は `ctx.Dull` を再び呼ぶので、
   敵側に `Relay` を持たせた瞬間に無限往復する。今は敵に誰もいないが、先に入れておく
2. **`Bear` と `Relay` の競合を決めること**（§2-1）。優先順位を固定すると片方が飢える。
   決めた側と理由を書く
3. **代金は `ApplyDamage` を通す。** 肩代わりが走るのは仕様だが、
   **自弁率を数えないと「代金を設計した」ことにならない**
4. **ワタの攻撃力は落ちない。** ワタは横取りするだけで自分の `AtkBonus` は動かさない
   （ウケは背負って 6.0 → 0.0 になった）。**代金はHPで払う**ので、
   ウケとは天井の種類が違う。この違いが波ごとの順位に出るかを見ること
5. **流し先が既に死んでいる場合。** `CurrentAttack` が最高の**生存**駒を選ぶこと。
   全滅していれば何もしない（横取りもしないか、横取りだけして捨てるかを決めて書く）
6. **召喚枠（スロット5〜8）の扱いを明記する。** 隣接表に召喚枠が含まれるので
   横取りの対象に入る。**含めたかどうかを報告書に書く**。推奨は「含める」
   （第42期の集約と揃える）
7. **乱数列がずれる条件を意識する。** `PickOne` は候補が2個以上のとき `Roll` を消費する。
   帰属は必ず `RelayRule(0)` かワタ抜きの対照で取る。前後比較で帰属しない
8. **長時間ジョブはフォアグラウンドで1ツール呼び出し内に収める。** 背景に回すと刈られる

1. Phase 0（§1）を走らせ、結果を報告書の冒頭に書く。
   **0-3（敵の攻撃力を 0 にするのに何点要るか）と 0-4（隣に置きたい駒）を先に出す**
