## 0. なぜこれをやるか

第144期でバサの転倒を採用したが、**実際に遊んだときに転倒が起きているか分からない。**

第四波（前1 城塞／前3 城塞／中央 軛／後1 詠唱兵／後3 従軍司祭）の実戦ログでは、
**機構は完全に設計どおり動いていた**:

| ターン | バサが動かした | 行が前に変わったか | その手番 |
|---|---|---|---|
| 1 | 従軍司祭→後1、詠唱兵→後3 | 後列どうし＝**変わらない** | 従軍司祭は普通に殴っている |
| 2 | 城塞→前1、城塞→前3 | 前列どうし＝**変わらない** | 3体とも殴っている |
| 3 | 従軍司祭→**中央**、軛→後1 | **前に出た** | **従軍司祭が行動順に居ない** |
| 4 | 詠唱兵→**前1**、城塞→後3 | **前に出た** | **詠唱兵が行動順に居ない** |
| 5 | 従軍司祭→**前3**、城塞→中央 | **前に出た** | **従軍司祭が行動順に居ない** |

**ターン4 がこの機構の一番いい仕事だった**——詠唱兵はターン3 で「魔力を集めている（次 ×2 全体）」と
溜めた直後に前へ引きずり出されて転び、**溜めた全体攻撃が1ターン遅れている**。
これが画面に一言も出ないのは、機構の価値がプレイヤーに届いていないということ。

### 何が足りないのか

**ログ行そのものは既にある**:

```csharp
// BattleEngine.cs:5309（転倒） / 5286（痺れ）
Log($"  {actor.Name} は転んで動けない", LogKind.Status);
```

足りないのは **`BattleEvent`**。受け流しは `Log` と `Emit(Kind = BattleEventKind.Parry)` の
**両方**を出しているから画面に出る（`DemoApp/Main.cs:941` ほかで受けている）。
転倒は `Log` だけなので、**イベントから絵を組み立てている側には存在しない。**

**まどろみ（ゴルムの巨躯）はこの期の対象ではない。** `ColossusRule` の doc が
「**還しは有効・まどろみは無効**（第36期）」と書いており、既定では1度も発火しない。
規則として残っているのは対照のため。

|---|---|---|
| `BattleSim` の verbose 出力 | `LogLine`（`Log(...)`） | ? |
| `DemoApp` のログ欄 | `LogLine` か `BattleEvent` か | ? |
| `DemoApp` / `GodotApp` の盤面 | `BattleEvent`（＋`EmitStatusSnapshot`） | ? |

**ポンは「画面上でもログ上でも分からない」と言っている**ので、
**`LogKind.Status` が表示側で落とされている可能性**も含めて確認すること
（`Log` は出ているのに画面に来ないなら、足すべきものが変わる）。

**痺れ（5286 行）についても同じ確認を並べる**——同じ形で書かれているので、
**痺れが見えていて転倒だけ見えないのか、両方見えていないのか**で原因が分かれる。
`sting`（追い打ち・シガ）は敵の `IdleTurn` を読む唯一の味方の機構なので、
**痺れた敵が見えていないならそちらも同じ穴**。

### Q0-2. `EmitStatusSnapshot` は `Stagger` を写しているか

`StatusKeys.All` に `Stagger` は入っていて、表示記号も `Stagger => "転"` が定義済み。
**スナップショットが9種全部を写しているなら、盤面のマークは既に出ているはず**なので、
出ていないならどこで落ちているかを特定する。

> **標・痺・破片のマークは Codex 側で反映済み**（ポン）。同じ経路に乗るなら、
> **この期で足すのは engine 側の1〜2行だけで、表示側は自動的に付く可能性がある。**
> その場合は表示側を触らない。

### Q0-3. `BattleEventKind` に種別を足すか、既存で足りるか

現在の種別: `TurnStart / Attack / Damage / Heal / Death / Summon / Revive / Move / Status /
Highlight / Charge / (Snapshot) / Parry ...`（**全数を確認すること**）。

- **`Status`（継続効果が働いた）で足りるか。** doc は「そのターン実際に削った量」と書いているので、
  手番を失ったことを表すのに合っているか判断する
- 足りないなら **`Stagger` を1つ足す**。`Parry` が第143期に足された前例と同じ形
- **足す種別は1つまで。** 「転んだ瞬間」と「失った瞬間」は `Amount` か `Text` で区別する

### Q0-4. `_verbose` の扱い

`Parry` の `Emit` は `if (_verbose)` の内側にある。**転倒も同じ扱いにするか**を決める。

- `_verbose` が偽のとき（`compare` などの大量試行）は**イベントを出さない**のが既定のはず。
  そうしないと 61,000 戦ぶんのイベントが積まれる
- **`_verbose` の内側に入れれば、盤面の判定にも性能にも影響しない**ことを確認する

### Q0-5. 過去に表示専用のイベントを足した期の手順を写す
`BattleEventKind.Parry` を足した期（第143期前後）を `design/*.md` で探し、
**何を検算したか**を写す。同じ検算をこの期でも行う。

## 1. 実装

### 1-1. 出したい2本

```
  詠唱兵 → 前1  ← 喧噪のバサ
  詠唱兵 は前へ突き出されて転んだ          ← ① 付いた瞬間（ターン頭・ShufflerTrait の中）
  ...
  ▶ 詠唱兵 の手番
  詠唱兵 は転んだまま動けない               ← ② 失った瞬間（TakeTurnCore・既存の Log 行）
```

**2本要る理由**: 付与はターン頭、消費は行動順の中で、**別のターンになりうる**。
片方だけだと「何が起きたか」か「なぜ動かないか」のどちらかが欠ける。

- ① は `ShufflerTrait` が `Stagger` を立てる箇所に `Log` ＋ `Emit` を足す
- ② は**既存の `Log` 行はそのまま**にして `Emit` を足す（文言を変えない——
  `BattleSim` の verbose を読んでいる診断が文字列で拾っている可能性があるので、
  **Q0-1 で確認してから**変えるなら変える）

### 1-2. 触らないもの

- **`ShufflerTrait` の判定ロジック**（誰が転ぶか）は1ビットも変えない
- `StatusKeys.Stagger` の付与・消費の条件
- `BraceRule`（第143期の味方側の転倒。既定 `Stagger: false` のまま）
- 盤面・乱数・順序

**`Emit` と `Log` の追加だけ。** 判定の中に `if` を1つも足さない。
