## 0. なぜこれをやるか

### 混乱の値打ちは「手番を1つ消す」ことではない

第144期でバサに転倒（前に出た敵は次の手番を失う）を入れて読み手なしの台で **+20.9**。
次の一手として混乱が挙がっているが、**転倒の上位互換ではない**:

- **敵の殉教者（第五波・庇い 75%）が、混乱した味方の攻撃を庇う。**
  転倒とは噛まなかった敵の防御機構が、混乱なら**敵自身の攻撃を吸う側に回る**
- **こちらの被弾変換軸には損になる。** ムド（怒り）・ガルド（受け流し）・ドハ（分かち）・
  セッキ（後備え）・リィカ（死の連鎖）は**殴られて育つ**ので、敵の攻撃が敵陣に向くと**収入が消える**
- つまり混乱は無条件の得ではなく、**被弾変換編成では代金になる**＝可変コスト型

### 敵が使ってきたときが本番

混乱させられた味方の攻撃が自陣の前列に飛ぶ。それを受けるのが誰かで意味が変わる:

| 前列にいるのが | 起きること |
|---|---|
| ガルド | **受け流しで無効化**。混乱が空振りする |
| ササ | 上限7で切って、**切り落とした分が隣の破片になる**。混乱が供給に化ける |
| ムド | **殴られて怒る**。自軍の攻撃で自軍のエンジンが回る |
| ゴルム | 飲み込んで還す |

**敵の妨害を自分の被弾軸で資産に変える**——ゲームの中心テーマの、攻撃側の版。

### だから駒ではなく波で測る

board-rule 系の標準手順（**ルールの効き方を波で測ってから駒に移す**）にそのまま乗る。
波ルールなら**両陣営に等しくかかる**ので、「敵が混乱を使ってくる形」の実験にも同時になる。
**駒にするならロスターの枠（キリを切る）が要るが、波なら不要。**

### Q0-1. 標的の集合はどこで作られているか（**設計の要**）

Web 側が読んだかぎり、`SelectTargetChain` の冒頭の**1行**に集約されている:

```csharp
List<UnitState> foes = LivingMembers(Opponent(attacker.TeamId)).ToList();
```

- **単体・薙ぎ・全体**はこの `foes` から `PoolOf` を作る
- **貫き**は `SelectPierceEntry(foes, out lane)` で手前に分岐するが、**同じ `foes` を受け取る**
- 薙ぎの巻き込みは `LaneOccupants(LivingMembers(entry.TeamId), lane)` —— **`entry.TeamId`**（標的側）を見ている

**確認すること**:
- この1行を `attacker.TeamId` に差し替えるだけで、単体・薙ぎ・貫き・全体の**4型すべて**が自軍に向くか
- **`attacker` 自身が `foes` に入らないように除外**する必要があるか（自分を殴る絵は出したくない）
- 巻き込み・貫き経路が `entry.TeamId` を見ているなら、**自軍を撃つときも正しく自軍の席で解決される**か
- **他に標的の集合を作っている箇所**（`Divert`／`Expose`／`Fixate`／`Sever` などの選好、
  敵側の `Shove`・`Slander`）が `Opponent(...)` を独自に呼んでいないか。**全数で数える**

### Q0-2. `isFriendlyFire` の扱い（**28 + 14 箇所。ここが山**）

`PerformAttack` の `ApplyDamage` 呼び出しは `isFriendlyFire` を**明示的に渡していない**（既定のまま）。
つまり**混乱した攻撃は「敵への攻撃」として処理される**。

`isFriendlyFire` は `BattleEngine.cs` に 28 箇所、`Traits.cs` に 14 箇所。**全数を分類する**:

| 分類 | この期の扱い |
|---|---|
| (A) **事故の帳簿**（惨禍・巻き込み則・自傷の計数） | 混乱を事故として数えるか？ **数えないほうが素直**（混乱は事故ではなく敵の妨害の結果）。決めて理由を書く |
| (B) **肩代わりの除外**（庇い・巨躯・分かちが「味方からの攻撃は庇わない」等） | **ここが判定を変える。** 混乱した攻撃を庇うか庇わないかで結果が大きく動く |
| (C) 表示・ログ | 影響なし |

**(B) を優先して確定させる。** 特に:
- **庇い（ガルド）・標的の介入**が「敵からの攻撃」に限定しているか
- **敵の殉教者（Martyr）**が自軍からの攻撃を庇うか（§0 の一番の狙い）
- **巨躯（ゴルム）・分かち（ドハ）・後備え（セッキ）・棘守り（カド）**の肩代わり条件

### Q0-3. 被弾変換の駒が `source` の陣営を見ているか

**混乱が「代金になる」という §0 の読みが成立するか**の根拠。以下が `source.TeamId` を見ているかを確認:

- **ムド（怒り）** —— 殴られると伸びる。自軍からの攻撃でも伸びるなら「混乱が味方のエンジンを回す」が成立
- **ガルド（受け流し）** —— 自軍の攻撃も無効化するか（するなら混乱が空振り）
- **ドハ（分かち）／セッキ（後備え）／リィカ（死の連鎖）**
- **ササ（身構え・第143期）** —— 上限7で切って切り落としを配るか（するなら混乱が供給に化ける）
- **ウケ（集約）／ウロ（鱗）**

**見ていない（陣営を問わない）なら §0 の表がそのまま成立する。** 見ているなら表を書き直す。

### Q0-4. 撃破イベントが「敵を倒した」を前提にしていないか

- **ハギ（追撃）／ノミ（執着）／ゾト・ムグ・ヴェル・ラウ（死亡トリガー）**
- 敵側の `Executioner`（撃破ごとに伸びる）が**自軍を倒したときも伸びるか**
- **味方が混乱して味方を倒したとき、リィカの層が積まれるか**——積まれるなら
  「混乱が死軸の燃料になる」という大きな相互作用。**予測に書く**

### Q0-5. 波ルールの置き方

既存の波ルール（粛・渇き・軛・断罪）と同じ作法で:

- **ルール保持者を1体置き、既存の敵と数値・型を完全同一にして差分を特性1つに閉じる**（対照の成立条件）
- `ConfusionRule`（`YokeRule` / `BraceRule` / `ShufflerRule` と同じ作法・**static にしない**）
- **どの波に載せるか**は決め打ちしない。§1-2 の候補から Phase 0 の材料で選ぶ

### Q0-6. 「動かされた」の定義

混乱の鍵は**席が動いたこと**。既存の動かす機構を全部列挙する:

- 味方側: バサ（喧噪）・ササ（身構えの弾き）・ハネ（突き返し）・シオ（移り木）・セロ（逃亡）・ガルド（庇いの前出）
- 敵側: `Shove`（突き飛ばし）・その他

**両陣営に動かす機構があることを確認する**（片方が 0 なら対称ルールの合否テスト1に落ちる）。
**庇いの前出（一時的な入れ替え）を「動かされた」に数えるか**は決めて理由を書く——
数えると庇い駒が毎ターン混乱して壊れる可能性が高い。

### Q0-7. 過去に「陣営を反転させる」実験が無いか
`design/*.md` に限定して `混乱` / `同士討ち` / `Confus` / `陣営.*反転` で走査する。

## 1. 設計

### 1-1. 混乱（`ConfusionRule`）

> 席を動かされた駒は、**次の1回の攻撃**を自軍に向ける。

```csharp
public readonly record struct ConfusionRule(bool Active, bool CountGuardStep)
```

- `Active = false` が既定（回帰の基準）
- `CountGuardStep` は Q0-6 の「庇いの前出を数えるか」。**既定は false**
- 鍵は `StatusKeys` に1つ足す（`Confused`）。**痺れ・転倒を流用しない**（読み手が混ざる）
- **1回だけ**。撃ったら落ちる。ターンをまたいで残る（動かされた次の手番が来るまで）
- **攻撃以外（`Skill`・`Charge`）は混乱しない**（標的選択を通らないので）。
  ただし `Charge` の次の一撃は混乱するか？ **決めて理由を書く**

### 1-2. どの波に載せるか（Phase 0 の材料で決める）

| 候補 | 根拠 | 懸念 |
|---|---|---|
| 新しい実験波を1本 | 差分が1つに閉じる | 帯が増える |
| **第五波（断罪＋殉教者）** | §0 の一番の狙い（殉教者が自軍の攻撃を庇う）が直接測れる | **波ルールが2つになる**——差分が2つ |
| 第二波 | 52行中22行が100%で飽和（診断済み）。課税先として筋が通る | 動かす機構が敵側に薄いかもしれない |

**決めるのは Phase 0。** 第五波に載せるなら「断罪＋殉教者＋混乱」で差分が2つになるので、
**対照は「第五波そのまま」と「混乱だけ足した第五波」**の2点で取る。

## 3. 予測（**Q0-2 / Q0-3 の答えが出てから確定させる。実装前に書き切り、外れても消さない**）

方向だけ先に書く。**Q0-3 で「陣営を見ている」と出たら書き直すこと。**

1. **被弾変換が厚い台で下がり、薄い台で上がる**（符号が割れる＝可変コスト型）。
   両方で上がるなら代金になっていない
2. **ササ同席の台では下がらない**（混乱の一撃を上限7で切って切り落としに変える）
3. **第五波に載せるなら、殉教者が自軍の攻撃を庇う**ので敵側の混乱の効きが弱まる
4. **混乱が死軸の燃料になる**（Q0-4 次第）。味方が味方を倒すとリィカの層が積まれるなら、
   死軸の台では**混乱が資産**になる
5. **動かす機構なしの台で発火 0**
6. **この波を含まない行は ±0.0**

## 5. 採否

### 採用の条件
1. **符号が割れる**（被弾変換の厚い台と薄い台で逆を向く）。一様に上がる／下がるなら、
   それは「手番を消す」の変種であって混乱ではない
2. **Q0-3 の表どおりの相互作用が実測で出る**（ガルドで空振り・ササで供給に化ける・ムドで怒る）
3. **この波を含まない行が ±0.0**

**壊れ気味は許容する。** ただし**全台が天井か床に張り付く**なら、混乱を「次の1回」から
「50% の確率で」に弱めた版を1点だけ測って報告する（採用はしない）。

### 止めてよい条件（**この期の重要な出口**）
**Q0-1 / Q0-2 で「陣営の前提が engine に散らばっている」と分かったら、
実装せずにその全数と分類を報告して終わってよい。**
そのとき報告書に書くべきは「**混乱を入れるには何を直す必要があるか**」の一覧。
それが次の期の指示書になる。

### 不採用のとき
`ConfusionRule` は残置（`Active = false` が現行と同値）。
