## 1. なぜこれをやるか

第10期で敵にチャージを入れたが、順位相関は 0.91 で軸は立たなかった（群差 0.064 波）。**ただしこれは「時間軸が無効」という結論ではない。**

- **相性が片側にしか無い。** 敵だけがパターンを持ち、味方は毎ターン同じ行動を繰り返す。「大技の前に回復を差す」「3T に自爆を合わせる」のような噛み合わせが**そもそも表現できない**
- **今の `ActionKind` は `Attack` と `Charge` だけ。** 回復・毒・バフといった能動的な効果は `Trait.OnTurnStart` に置かれていて、**毎ターン無条件に発火する**。タイミングという概念が存在しない

コンセプトメモ（`design/行動パターン化検討メモ.md`）の狙いは「何ターン目にシナジーが成立するか」だった。それを表現するには**スキルを手番の行動として扱える**必要がある。

**この作業の核心は `ActionKind.Skill` の導入。** 味方に `Charge → 強攻撃` を配るだけなら、第10期と同じ弱い結果（0.064 波規模）を再現するだけになる可能性が高い。**そう予想していることを明記しておく。**

## 3. Phase BA — のろまを `Actions` へ移す

### 3-1. なぜ最初にこれか

`SluggishTrait`（`Traits.cs:267`）は `CanAct` で `ctx.Turn % 2 == 1` を返す。**これは実質的にチャージそのもの**で、特性として書かれているだけ。`Actions = [Charge, Attack]` に置き換えられるはず。

**置き換えて `compare` が動かなければ、仕組みが既存の挙動を表現できることの証明になる。** 動くなら、どちらかに未知の差がある。

### 3-2. 注意点

- **`SluggishTrait.CanReact`（`Traits.cs:281`）が偶数ターンの割り込みも止めている。** `Actions` に移すと、この「割り込みでも動けない」が失われる。現ロスターにのろま＋割り込みの同居は無い（コメントにそう書いてある）ので `compare` は動かないはずだが、**失われること自体は事実なので、特性を残して併用するか、`Actions` 側で再現するかを判断して報告する**
- **ターン奇偶の一致。** `Actions = [Charge, Attack]` だと T1 が Charge・T2 が Attack。`Sluggish` は T1 に動く。**位相が逆**。`[Attack, Charge]` が正しいはず。**ここは実際に測って確かめる**
- **`IdleTurn`。** `Sluggish` は `SurrendersTurn` を偽にしている（`Traits.cs:679` か `1425` のどちらか）ので号令・据えに売られていない。チャージも `IdleTurn` を書かない実装（第10期 AA）なので一致するはず。**確認して報告する**

### 3-3. 受け入れ条件

- `compare` / `chain` / `pulse` / `ablate` / `dump` / `engage` / `seats` / `handoff` / `cost` / `gradient` / `aim` / `flip` / `bridge` / `bill` / `charge` の差分 **ゼロ**
- 差分が出た場合、**原因を特定して報告する。数値で辻褄を合わせない**

## 4. Phase BB — `ActionKind.Skill` の導入

### 4-1. 仕組み

```csharp
public enum ActionKind { Attack, Charge, Skill }
```

`Trait` に手番で呼ばれるフックを足す:

```csharp
/// <summary>手番の Skill 行動で呼ばれる。OnTurnStart（毎ターン無条件）と違い、
/// 行動パターンに載った駒だけが、載せたタイミングで実行する。</summary>
public virtual void OnAction(BattleContext ctx, UnitState self, UnitAction action) { }
```

**`Skill` の手番は攻撃を消費する。** これが要点で、「回復と攻撃のどちらを取るか」が生まれて初めてタイミングに意味が出る。**攻撃もして回復もする**なら今と変わらない。

### 4-2. 移行する2体

| 駒 | 現状 | 移行後 |
|---|---|---|
| 継ぎ当てのノノ（`nono` 78/3/6・繕い） | `MenderTrait.OnTurnStart` で毎ターン回復 + 攻撃3 | `Actions = [Skill]`、`OnAction` で回復 |
| 澱みのミオ（`mio` 42/2/8・澱み） | `AmplifierTrait.OnTurnStart` で毎ターン毒+4 + 攻撃2 | `Actions = [Skill]`、`OnAction` で毒濃縮 |

**`[Skill]` 1つだけのパターンで移行する。** これで挙動の差は「攻撃3（ノノ）/ 攻撃2（ミオ）が出なくなる」だけになり、**移行そのものの影響を最小にできる**。`compare` は動くが、動く量が小さいことが移行の正しさの傍証になる。

**動いた行と量を報告すること。** ノノ・ミオを含む編成だけが動くはずで、含まない編成が動いたら移行の実装が漏れている。

### 4-3. 発火順序に注意

`OnTurnStart` は**ターン頭に全員分**が走る（`BattleEngine.cs:987`）。`OnAction` は**素早さ順の自分の手番**で走る。つまり移行すると**発火が遅くなる**。

- ノノの回復は「ターン頭に最も傷ついた味方を繕う」から「ノノの手番に繕う」へ。速度6 なので、**それより速い味方が殴られた後**に回復が入る
- ミオの毒濃縮は「ターン頭に濃くする」から「ミオの手番に濃くする」へ。**毒の判定（`TickStatuses`）との前後関係が変わる可能性がある**

**これは仕様変更なので、意図した変更として README に書く。** ただし**毒の tick とミオの濃縮の前後が入れ替わって、毒のダメージが1ターンずれるようなら止まって報告する**（それは移行の副作用として大きすぎる）。

### 4-4. 受け入れ条件

- 動くのはノノ・ミオを含む編成**だけ**
- `dump` でノノ入り編成のログを見て、回復がノノの手番に入っていることを目視確認し、報告に貼る

## 5. Phase BC — 変種を作って測る

### 5-1. 変種

移行した2体に、**パターンだけが違う変種**を作って比較する。**特性の数値は変えない。**

| 変種 | ノノ | 意図 |
|---|---|---|
| N0（基準） | `[Skill]` | 毎ターン回復。移行直後の形 |
| N1 | `[Skill, Attack]` | 回復が隔ターン。手番の半分を攻撃に使う |
| N2 | `[Skill, Skill, Attack]` | 3ターン周期 |

ミオも同様に M0 / M1 / M2。

**変種は `UnitCatalog` の定義を書き換えるのではなく、診断モードのローカルで差し替えて測る**（`gradient` / `aim` が候補波をローカルで組んだのと同じやり方）。`UnitCatalog` は N0 / M0 のまま。

### 5-2. 測る場所と指標

**測定台は第10期 AB-0 で新設した台（`bridge` の7列目）と、既存5波の両方。** 第8期の「136% で測ると何も見えない」は引き続き有効。

1. **順位相関**（第8期・第10期と同じ計算方法。**方法を変えない**）— **これが本番**。第10期の 0.91 を下回るか
2. **群差**: 回復持ち / 非回復、毒軸 / 非毒軸。第10期の 0.064 波、第9期の 0.131 波と並べる
3. **敵の大技ターンとの噛み合わせ**: 詠唱兵・狙撃手が大技を撃つターンに、ノノの回復が乗っているか。**変種によってここが変わるか**（N1 は隔ターンなので、周期が敵と揃うか揃わないかで差が出るはず）
4. ターン数 — 間延びしていないか

### 5-3. 判定

| 観測 | 結論 |
|---|---|
| 順位相関が 0.7 を明確に下回り、変種で編成の序列が変わる | **タイミングが軸になった。** 味方側の展開を広げる段階 |
| 変種間で結果がほとんど変わらない | **タイミングは効かない。** スキルをいつ撃つかは、撃つ回数の多寡に吸収されている |
| N1/N2 が N0 より一律に弱い（回数が減っただけ） | 同上。**「回数」と「タイミング」が分離できていない**ので、そう報告する |
| 敵の大技ターンとの位相で結果が割れる | **これが出たら一番大きい。** 時間軸の相性が実在する証拠なので、数字を厚めに報告する |

**§5-3 の2行目・3行目が出た場合、「時間軸は軸にならない」がほぼ確定する**（敵側・味方側の両方で試して届かなかったことになる）。その場合も結論として記録し、次は別の方向を探す。

## 7. 作業ルール

1. マージ → BA → BB → BC → BD の順。**フェーズを跨いで1コミットにしない**
2. コミットメッセージに「動いた docs/ の行」を書く。BA は差分ゼロ、BB は動く
3. コード・コメント・ログは日本語。既存の文体（**却下した案とその理由も書く**）に揃える
4. CONTRIBUTING.md のチェックリストを通す。`Trait` にインスタンスフィールドを足さない / 再入フラグを static に置かない / `LivingMembers` はスナップショットで使う
5. 長時間ジョブは前景で待ち切る。`layout` は走らせない
6. **数値を調整しない。** 変種で何かが壊れて見えても、記録して報告する
7. 以下を見つけたら**実装前に止まって報告する**:
   - BA で `compare` が動いた場合
   - `Skill` が手番を消費する設計で、既存の特性が壊れる場合（例: `OnTurnStart` の発火を前提に他の特性が組まれている）
   - 毒の tick とミオの濃縮の前後が入れ替わり、毒のダメージが1ターンずれる場合
   - ノノ・ミオを含まない編成が動いた場合
