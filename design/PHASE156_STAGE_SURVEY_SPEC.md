## 0. なぜこの期を立てるか

### 0-1. いま起きていること

第153・154・155期の3期、新しいヒーラーの設計で連続して空振りした。
判定の線は毎回「マイナスの符号が編成で反転するか」に置いたが、**3期とも落ちた**。

原因を遡ると、**判定の単位が合っていない**可能性が高い。
現在のロスター評価（`compare` 61行・`checkup` 1,326組）は**単発戦の勝率**しか見ていない。
ところが本編のゲームは次の形で構想されている。

| 本編の仕様（構想） | 単発戦の `compare` に入っているか |
|---|:-:|
| HP は戦闘をまたいで持ち越す | × |
| 倒れた駒はそのステージ中リタイア（復帰の可否は未定） | × |
| 味方は段階的にランダムに到着し、配られた中で編成を組む | × |
| 部隊は5枚。味方が増えるほど編成できる部隊が増える（最大10部隊想定） | × |
| 複数部隊が**同時進行**（RTS）。どこを攻め、どこを守るかをプレイヤーが決める | × |
| 負けても2部隊目で勝てる（敵も同じ） | × |
| ステージは 1-1〜1-5 のように進み、後半ほど当たる部隊が増える | × |
| 第三勢力が出て敵同士が戦う／味方の自律部隊が出る（構想） | × |

**駒の価値が単発戦の勝率では表せない例が既に複数ある。**

- **爆ぜるゾト**——単発戦では「燃焼用のライター」か「リィカの餌」でしかないが、
  持ち越しがあるなら**特攻・玉砕部隊として敵を削る**という独立した使い道が立つ
- **継ぎ当てのノノ**——2〜3回繕うと尽きる。単発戦では勝率に出るが、
  **ステージ単位では「駒1枚を失う」というコスト**であり、`compare` に1ビットも現れない
- **熾のホタ**——自分では点火できないが、**敵が燃焼を付けてくる相手にぶつければ機能する**。
  「どこへ送るか」が選べる前提でしか成立しない価値

### 0-2. この期の問い

> **いまある `Engagement` で、ステージ単位の駒の評価はどこまでできるのか。
> できないのは何で、それを埋めるのにどれくらいかかるのか。**

**答えを出すだけでよい。** 作るかどうかは次の期にポンが決める。

## 1. 調べること

### Q1. `Engagement` は何を持っているか（**実装を読む**）

`BattleCore/Engagement.cs`（466行）と `design/ENGAGEMENT_PLAN*.md`（9本・計約1,900行）を読み、
**実装されているもの**と**計画だけで終わっているもの**を分けて表にすること。

最低限、次の項目について「実装済み／計画のみ／無い」を判定する。

| 項目 | 状態 | 根拠（ファイル・行） |
|---|---|---|
| HP の持ち越し | | |
| 最大HP の損耗の持ち越し | | |
| 蘇生回数・層など特性の状態の持ち越し（`Trait.OnCarryOver`） | | |
| 境界で消えるもの（`StatusKeys` 全部・`AtkBonus`） | | |
| 倒れた駒の扱い（次の Battle に出るのか、抜けるのか） | | |
| 拠点回復に相当するもの（`RecoverRule`） | | |
| 味方が複数部隊あるときの挙動 | | |
| 引き分け（`MaxTurns` 到達）の扱い | | |
| 特攻の価値を測る指標（`FirstBattleAttrition` / `LastBattleAttrition`） | | |

> `EngagementResult` の doc に「**最初の Battle で敵第1部隊の総 MaxHp のうち削った割合。特攻隊の価値を測る**」
> と明記がある。**これがゾトの用途にそのまま使えるか**を判定すること。

### Q2. 会戦を使っている診断は何を答えているか

`EngagementEngine.Run` を呼んでいる診断を全部挙げ、**それぞれが何を測るための道具か**を1行で書く。
（`BattleSim/Common.cs` のほか `Power` / `Recover` / `Timing` / `Engage` / `Charge` /
`Bridge` / `Seats` / `Gradient` / `Betray` などに呼び出しがある。**grep で全部拾うこと**。）

**そのうち「駒1枚の価値をステージ単位で測る」ものが既にあるか**を判定する。
無いなら、**一番近いのはどれか**を挙げる。

### Q3. `compare` / `checkup` を会戦の単位に載せ替えるコスト

現在の器具:

- `compare` — 61編成 × 5波 × seed 0..199。単発戦
- `checkup` — 52枚 × 1,326組。単発戦。所要約20分

**これらを「ステージ（会戦）を1単位」にすると何が変わるかを見積もること。**

- 何を差し替える必要があるか（台の作り方・判定式・出力の形）
- 計算量は何倍になるか（1ステージ = 何 Battle 相当か）
- **既存の判定の線（歯止め 33.2・情報セル・拒否権）はそのまま使えるか、作り直しか**

> **見積もりであって実装ではない。** 数字は桁が合っていればよい。

### Q4. 本編の仕様と会戦の差分

§0-1 の表の8項目それぞれについて、**会戦で表現できるか**を判定する。

できないものは、**engine の改修が要るのか、診断側で足りるのか**を分けること。
特に次の3つは構造に関わるので重点的に見る。

1. **倒れた駒のリタイア**——いまの会戦は「倒れた駒は Hp 0 のまま数に入る」とある。
   ステージ単位では**次の戦闘に出られない**のが正しいが、実装がどちらか
2. **複数部隊の同時進行**——いまの会戦は「同じ地点で部隊列が尽きるまで連結する」＝**逐次**。
   RTS の同時進行とは形が違う。診断としては逐次で足りるのか
3. **ランダム到着**——「配られた中で編成を組む」を測るなら、
   **編成を固定して測る現在のやり方が成り立たない**。`checkup` のドラフト台（埋め草を無作為に引く）が
   既に近いことをしているので、**そちらが流用できるか**

### Q5. 過去にこの単位で測った期があるか

`design/` の各期報告書を grep する。特に会戦計画9本のどれが実行され、どれが棚上げになったかを整理すること。
**「測ったが採らなかった」ものがあれば、その理由を引くこと。**
