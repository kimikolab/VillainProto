## 0. この期の主題

**アーマー（`StatusKeys.Armor`）に初めての読み手を作る。**

アーマーは6つの盤面状態キーの中で**読み手が0枚の唯一の資源**である（Phase 0-1 で数え直すこと）。
そして性質が他と違う。

- **`ApplyDamage` で HP の前に削られるプール**。回復とは別資源
- **`AcceptsSupport` を貫通する**（砕けの doc に明記）。
  「誰の助けも届かない」駒（ガルドの `Stoic`）に唯一届く支援
- **プールにしてあるのは「引き算は崖」を避けるため**。1発を完全に吸う形にすると
  敵の一撃を超えるか超えないかで二値になる

**隣接を1つも使わない。** 第45〜46期で隣接は2期かけて否定的な結論が出ている
（隣接依存の最頻率85%、驕りに至っては100%で第45期のどれより固定された）。
読むのは自分が纏っている量なので、席の問題から完全に外れる。

### 供給の現状（設計の制約）

**他人にアーマーを配れる経路は1本しかない。**

| 供給 | 誰に | 条件 |
|---|---|---|
| 砕け（ヒビ・`ShatterTrait`） | **味方全体**（自分を除く） | **範囲攻撃を受けたときだけ**。単体攻撃では何も起きない |
| 集約（ウケ・`BearTrait`・第42期） | **自分だけ**（`taker`） | 隣接する味方が弱体を受けたとき |

つまり読み手を単体で作ると、**供給が波依存の1本しかない台**になる。
第44期の誹り（保持者が2.70Tで落ちて供給が枯れ、横取り率4.2%が `Penalty` を3倍にしても
動かなかった）と同じ轍になる。

**だから読み手自身に供給経路を持たせる。** ただし自己完結させない——
供給の条件は**他人の身に起きる出来事**にする。

## 3. 実装

### 3-1. 特性 `TraitId.Scale`（鱗）

```
Scale,       // 鱗: 倒れた味方の破片を拾って纏う。纏っているあいだ攻撃が貫きになるが、
             // 振るたびに剥がれる（供給・発揮・消費の1サイクルが1枚に入る）
```

**プラス・マイナスのどちらのブロックにも入れない。**

#### 供給 —— `OnAllyDeath`

味方が倒れるたび、自分の `StatusKeys.Armor` に `GainPerDeath`（定数 4）を加算する。

- **`AcceptsSupport` を見ない。** 砕けと揃える——
  アーマーは damage 側で消費されるプールであって回復でも強化でもないので、`Stoic` を貫通する
- **自分の死では発火しない**（当然だが明記）
- **供給が他人の死である点が要点。** 自分では作れないので自己完結しない

#### 発揮 —— `ModifyPattern`

`Counter(StatusKeys.Armor) > 0` のとき、攻撃型を**貫き（Pierce）**にする。

- `ModifyPattern` の既存実装（把握では3つ）と**同じ形で書くこと**
- **貫きは「後列に届く」経路**なので、この駒は
  **アーマーを纏っているあいだだけ後列に手が届く**ことになる

#### 消費 —— `OnAfterAttack`

攻撃するたび `Armor` を `CostPerAttack` だけ減らす（0 未満にしない）。

- **読むことが消費になる。** アーマーは被弾でも削られるので、
  **攻撃と被弾の二重支出**になり、供給が細ければすぐ枯れる
- **これがこの駒のマイナス側。** 「盾を削って刃にする」という1つの動作の表と裏

### 3-2. 強度のノブ `ScaleRule`

```
public readonly record struct ScaleRule(int CostPerAttack)
{
    public static ScaleRule Default => new(1);
}
```

- 掃引は **0 / 1 / 2**
- **`CostPerAttack = 0` は「消費しない」＝維持型になる。**
  つまりこのノブは強度ではなく**性質**（維持型か消費型か）を切り替える。
  第41期の掃引が「比が全点で 2.30 で動かない＝ノブは強度しか変えない」に終わったので、
  **性質を動かすノブを選んである**
- `GainPerDeath` は定数 4（`ScaleTrait` に置く）。**振らない**
- `BattleEngine.Run` の引数に足す（既存の各 `Rule` と同型）。**static のノブは置かない**

### 3-3. 駒 `UnitCatalog.Uro`（鱗のウロ）

```
Id = "uro", Name = "鱗のウロ", MaxHp = 70, Attack = 9, Speed = 7,
Traits = { TraitId.Scale }, Pattern = AttackPattern.Single
PlusText  = "味方が倒れるたび破片を纏う。纏っているあいだ攻撃が貫きになる"
MinusText = "振るたびに剥がれ、殴られても剥がれる。自分では破片を作れない"
Flavor    = "倒れた者の欠片を拾って身に着ける。誰も惜しまないから、いくらでも拾える。"
```

数値は探索段階の初期値。**掃引の対象は `CostPerAttack` だけ**で、HP・攻・速は振らない。

### 3-4. compare への追加 —— **2行**（供給源を変える）

```
("鱗 (ウロ×死軸)", ...)     ← 供給が「味方の死」の台
("鱗改 (ウロ×ヒビ)", ...)   ← 供給に「砕けの破片」を足した台
```

- **2行の供給源を変えるのがこの期の設計。**
  死は波が進むほど増え、破片は敵の範囲攻撃がある波でしか出ない。
  **供給の時間分布が違う2つの台で、貫きが立つ時刻が変わるか**を見る
- 相方は Phase 0-3（敵の範囲攻撃の分布）と Phase 0-4（死亡数の分布）から選ぶこと
- **予算壁に注意。** 直近3期で後半2波に届いたのは
  「供給兼土台→読み手の2枠」に収めた台だけだった。**払い出しを増やさない**
- 配置は §1 の作法で決める

**既存48行は1つも触らない。**

## 4. 診断モード `scale`

`BattleSim` に追加する。**出力は `docs/` に置かない**。
`CompareBuilds()` / `Stages` / `Columns` を触らないこと。

| 列 | 中身 |
|---|---|
| 獲得 | アーマーの獲得量/戦・**内訳（味方の死 / 砕けの破片）** |
| 纏い率 | `Armor > 0` だったターン数 / ウロの生存ターン数 |
| **初纏い** | **初めてアーマーを得たターン**（供給の立ち上がり） |
| 貫き | 貫きで攻撃した回数/戦 |
| **後列到達** | **貫きが実際に後列の敵に当たった回数**/戦 |
| 支出・攻 | 攻撃で消費した量/戦 |
| 支出・被 | 被弾で吸われた量/戦 |
| 枯渇 | `Armor` が 0 に戻った回数/戦 |
| 死蔵 | 使われずに終わった量/戦 |

**「貫き」と「後列到達」を分けて数えること。** 第42期は「生成したアーマー」ではなく
「実際に吸った量」で判断し、第43期は「流した量」ではなく「効き」で判断した。
**貫いた回数は成果ではない**——後列に敵がいなければ単体攻撃と同じである。

**「支出・攻」と「支出・被」を分けること。** 二重支出のどちらが律速かで、
この駒が「攻撃型」なのか「防御型」なのかが決まる。

**陽性対照を必ず置く**: `ScaleRule(0)`（消費しない）と、ウロを外した同じ編成の2本。

**発火しなかったことは盤面の値に痕跡を残さない**ので、ログか `Events` から数えること。

## 5. 予測（実装の前に書き、報告書に当否を載せる）

**軸の名前ではなく、窓口を通る駒の在庫で書くこと。**
第44期は「保持者の生存ターン数」、第46期は「削って条件を満たす経路」（実測1400戦で0件）を
外している。**どちらも供給が実際に流れるかを数え損ねていた。**

実装の前に以下を書き出す。

1. **2つの台それぞれの「初纏い」ターン**を波ごとに計算する。
   死軸の台は Phase 0-4 の死亡数、ヒビの台は Phase 0-3 の敵の範囲攻撃から引く。
   **敵に範囲攻撃が無い波では、ヒビの台の供給はゼロになるはず**
2. **纏い率**。獲得（死1件につき4）と支出（攻撃1回につき `CostPerAttack`＋被弾）の収支から、
   **定常状態で `Armor > 0` を保てるか**を計算する。
   第37期に「供給 1/T × 全消費 = 定常在庫1」という同型の計算をしている
3. **後列到達が貫きの何割になるか。** 敵の後列が生きている時間帯に貫けるかどうか。
   **敵の後列が先に落ちる波では、貫きは無駄になる**
4. **`CostPerAttack = 0`（維持型）と 1（消費型）でどちらが強いか。**
   0 は永続貫きになるので強いはずだが、**0 が明確に強いならこのノブは
   ただの弱体化ノブであって性質を切っていない**ことになる
5. **第五波・第四波の値**（Phase 0-8 の計算から）。
   **後半2波に届くかどうかが直近4期の共通の壁**
6. **`seats2` で2行の席がどうなるか。** 隣接を使わないので、
   **第45期の対照（最頻率65%）に近いはず**。近くなければ理由を考える

**予測を外したら、外した理由を報告書に書く。** 当てることが目的ではない。

## 7. 実装上の注意（既知の落とし穴）

1. **アーマーで受け切った被弾では被弾トリガーが呼ばれない**
   （`Traits.cs` のフックの doc に明記されているはず。Phase 0 で確認すること）。
   **ウロがアーマーを厚く纏うと、被弾を条件にする味方の特性が発火しなくなる**可能性がある。
   台に被弾トリガーの駒を入れる場合は、この干渉を診断で確認して報告書に書くこと
2. **`AcceptsSupport` を見ない**（§3-1）。砕けと揃える。
   既存の弱体経路とは扱いが違うが、**アーマーは damage 側の資源なので砕けに揃えるのが正しい**
3. **`ModifyPattern` は毎回評価される。** アーマーは戦闘中に増減するので、
   貫きは立ったり消えたりする。**フラグで固定しないこと**
4. **貫きの減衰を確認する。** 貫きが後列に届くときに減衰があるなら、
   「後列到達」の数え方に反映すること（当たった回数と与えたダメージの両方）
5. **`GainPerDeath` は定数。** ノブを2つにしない。
   第46期は1変数に絞ったおかげで「削って条件を満たす経路が1400戦で0件」を
   はっきり切り分けられた
6. **召喚枠の死も `OnAllyDeath` を通るか確認する。** 胞子・亡骸のような
   一時的な駒が倒れたときに供給が湧くと、**供給が無限に近くなる**。
   通るなら**除外するか、通ることを明記して測る**。判断と理由を報告書に書くこと
7. **乱数列がずれる条件を意識する。** 帰属は `ScaleRule(0)` かウロ抜きの対照で取る
8. **長時間ジョブはフォアグラウンドで1ツール呼び出し内に収める。** 背景に回さない。
   第45期の `seats2` は 8.4秒/行
