### Q0-1. 行動順の確定箇所（`BattleEngine.cs`）

Web 側が読んだ形と**一致した**。実体は `BattleEngine.cs:6600` 付近:

```csharp
bool inverted = ctx.AllUnits.Any(u => u.IsAlive && u.HasTrait(TraitId.Inversion));
var speedGroups = ctx.AllUnits.Where(u => u.IsAlive).GroupBy(u => (u.Def.Speed, u.TeamId));
var order = (inverted ? speedGroups.OrderBy(...) : speedGroups.OrderByDescending(...))
    .ThenBy(g => g.Key.TeamId)
    .SelectMany(g => { var tie = g.ToList(); ctx.Shuffle(tie); return tie; })
    .ToList();
```

- **毎ターン振り直している**（`for (turn...)` ループの中）。開戦時の `opening` は別物で、
  あちらは生贄・呪詛の適用順（`OnBattleStart` の通知順）
- `ctx.Shuffle(tie)` は**群ごとに乱数を消費する**
- `ThenBy(TeamId)` は触っていない

### Q0-2. 乱数をずらさずに「1体だけ先頭へ出す」

指示書の推奨どおり、**`order` が `.ToList()` で確定した後**に `Remove` → `Insert(0, …)`。
`speedGroups` にも `Shuffle` にも触っていないので**乱数の消費が規則の有無に依らない**。
**検算は `compare` 305 セルが `docs/balance.md` と 0 件差分**（`haste check` (a) で ○）。

### Q0-3. 「先頭へ出す」の意味

`order` は両陣営が混ざった1本のリストなので、**先頭へ出すと敵全員より先に動く。**
第2〜5波の敵の最速は 11 / 14 / 8 / 14 で、**味方の最速（キリ・ササ・セロ 速12）でも
第3・5波の勇者候補 速14 には勝てない**——つまりこの規則は
「味方の最速でも買えない席」を毎ターン1枚に配っている。**測りたいものとして妥当と判断した。**

### Q0-4. 対象の選び方（2点）

**S（遅い）＝ 生存味方のうち `Def.Speed` 最小 ／ A（強い）＝ `CurrentAttack` 最大。**

```csharp
if (ctx.Haste.Pick != HastePick.None)
{
    UnitState? pick = null;
    foreach (UnitState u in order)
    {
        if (u.TeamId != BattleContext.PlayerTeam || !u.IsAlive) continue;
        if (pick is null) { pick = u; continue; }
        bool better = ctx.Haste.Pick == HastePick.Slowest
            ? u.Def.Speed < pick.Def.Speed
            : u.CurrentAttack > pick.CurrentAttack;
        if (better) pick = u;
    }
    if (pick is not null && order[0] != pick)
    {
        int before = order.Count;
        order.Remove(pick);
        order.Insert(0, pick);
        ctx.HasteMoves++;
        if (order.Count != before) ctx.HasteCountMismatch++;
    }
}
```

- **`record struct` に計算プロパティを足していない**（第148期の穴。`docs/rules.md` の既定値の列が動く）
- **新しい規則・窓口・乱数の消費は 0**

| # | 予測 | 実測 | 判定 |

| 1 | `Slowest` のほうが `Strongest` より大きい | S **+2.7** / A **+5.1** | **×**（逆） |

### 予測1・4 が外れた理由 —— 速さと攻撃力が相関していない

`Slowest` が拾うのは **ゴルム（攻6）19 行・ガルド（攻9）19 行**、つまり
**62% の行で前倒しされるのは「遅くて弱い壁」**である。
**先に動いても、殴る力が無ければ手番は出力にならない**（第105期「手番は与ダメージの通貨」）。
一方 `Strongest` はドルガ 38 やボルグ 18 を毎ターン先頭へ出すので、
**同じ1手番でも払い出される量が桁で違う。**

> **「余地が大きいほうが効く」は、余地を使える駒にしか当てはまらない。**
> 第144期の「効き方は生の pt ではなく余地に対する取り分で見る」を持ち込んだが、
> **取り分を取れるかどうかは席ではなく打点で決まっていた。**

### 予測5 が外れた理由 —— **分母がターン数の量を版間の不変量にしていた**

`Remove` してから `Insert` するので **1ターンの `order` の要素数は変わらない**。
だが順序は盤面を動かすので**決着ターン数が動き**（7.88 → 7.43）、
**`TurnLoopCalls` は「全ターンの延べ」なのでそれに引きずられる。**

**第113期「『計数が版に依らない』を検算にするときは、その計数の分母がターン数でないかを見ること」
の完全な再発**である。指示書 §5-4 はこれを受け入れ条件に置いていた。

**線は動かしていない**（第64期）。× のまま記録したうえで、
**成り立つ側の不変量を engine に足した**——`HasteCountMismatch`（前倒しが `order` の
要素数を変えた回数）は **0**。

## 6. この期で残るもの

### 残置したもの

- **`HasteRule`（既定 `HastePick.None`）と `HastePick`**。ノブを振れば3版がそのまま再現する
- **計数2本**（`BattleResult.HasteMoves` / `HasteCountMismatch`）。どの規則も読まない

### 次の一手の提案

**「行動順を買う駒」は作らない。** 上界が +5.1pt で、代金の相場（第148期の −5.9〜−23.0）に届かない。

ただし**表C が1つだけ筋を示している**——**標の軸（駆り立て・止め・仇討ち）だけは +15〜+21pt 動く。**
これは「行動順が高い」のではなく**「標は書いた次の手番までに殴られると外れる」**という
機構固有の穴で、**行動順ではなく標の持続の側で解くほうが安い**
（例: 標を「書いた本人の次の手番まで」ではなく回数で持たせる）。
**通貨の値段ではなく、特定の機構の穴として次期に回す。**

### 数えたが使わなかったもの

- **`Slowest` が拾う駒の分布**（ゴルム 19 / ガルド 19 / ヒビ 4 / バン 4 / ドハ 4 / セッキ 3 /
  カド 3 / シガ 2 / トメ 1 / トモ 1 / ムグ 1）。
  **「いちばん遅い駒」を選ぶ規則は、実質2枚を選ぶ規則である**
  ——第62期「『一番◯◯な隣』型の選択子は、向きが本体ではない。本体はその端に誰が立っているか」の
  **盤面全体の版。**
