### 真因 —— **`Run` の引数ではなく、`<Main>$` のフレーム**

第138期は「引数を2本増やしたから」と読んだ。**引数は最後の一押しで、原因ではない。**

`BattleSim/Program.cs` は **68,000 行がトップレベル文**で、C# はそれを**1つの `<Main>$`** に畳む
——**全モードの局所変数が1つのスタックフレームに同居する。** 実測:

| モード | 落ちた場所 |
|---|---|
| `compare` | `ApplyDamage` の再帰（棘の反撃・数千段） |
| `compare quality` | **`<Main>$` の中の `Enumerable.Sum`**（再帰ではない。ただの集計） |
| `chain` | 同上 |
| `sever` | `ApplyDamage` の再帰（貫き経由） |

> **`Enumerable.Sum` の1呼び出しで落ちる**なら、それは再帰の深さの問題ではない。
> **`<Main>$` のフレームだけで既定 1MB をほぼ食い尽くしていた。**

### 直し —— **トップレベル文をやめて、本体を大きなスタックのスレッドで走らせる**

    // BattleSim/Program.cs
    internal static class Prog { internal static void Body(string[] args) { ...68,000 行そのまま... } }

    // BattleSim/Entry.cs（新規）
    internal static class Entry
    {
        static void Main(string[] args)
        {
            var worker = new Thread(() => Prog.Body(args), 256 * 1024 * 1024);
            worker.Start(); worker.Join();
        }
    }

- **中身は1行も動かしていない**（`class` と `Body(string[] args)` で囲っただけ。
  局所変数もローカル関数も並びもそのまま——トップレベル文はもともと `<Main>$` の本体なので、
  **生成されるコードはほぼ同じ**）
- **盤面・乱数・順序には1ビットも触っていない。** 変わるのは既定 1MB のスタックが
  256MB の**予約**になることだけ（予約は仮想アドレスで、実際に触ったページしか物理メモリを使わない）
- **例外は `ExceptionDispatchInfo` で投げ直す**——スレッドの中で握り潰すと、
  診断が黙って途中で終わって「生成物が作れた」ように見える

**採らなかった形を2つ残す:**

1. **`compare` の分岐だけをローカル関数に切り出して渡す版** ——
   **本体が参照するトップレベルの局所変数がすべて表示クラスへ巻き上げられ、
   Roslyn（VBCSCompiler）がメモリ 52GB を掴んでビルドが終わらなくなった**（実測）。
   **囲うなら全部。部分的に囲うとクロージャになる。**
2. **1戦だけを大きなスタックのワーカーへ渡す窓口（`BigStack`）** ——
   一度入れて `compare` は通ったが、**`compare quality` が `<Main>$` の集計で落ちて破綻した**。
   真因が分かった時点で**削除した**（機構を2つ持たない）

**`Run` の 49 本の引数を1つの束に畳む構造的な直しはやらない**——呼び出し口が数百あり、
**「計測器と測定対象を同時に動かさない」**に正面から反する。
**引数の本数はもう律速ではない**（1MB → 256MB で 256 倍の余裕ができた）。
